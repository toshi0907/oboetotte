# 位置情報の更新履歴(デバッグ)

**位置情報の更新履歴(デバッグ)**: `data/LocationUpdateLog`(`id`/`timestamp`/`type`〈`data/LocationUpdateType`の`ENTER`/`EXIT`/`PERIODIC`〉/`taskTitle`〈ENTER/EXITの場合のみ設定〉/`latitude`/`longitude`/`accuracy`/`detail`/`distanceMeters`・`radiusMeters`〈いずれもENTER/EXITの場合のみ設定、任意〉)として、ジオフェンスのENTER/EXITイベント受信と定期的な現在地取得の両方を記録します(`LocationUpdateLogDao`、`AppDatabase`バージョン12→13の`MIGRATION_12_13`、`distanceMeters`/`radiusMeters`はバージョン14→15の`MIGRATION_14_15`で追加)。`GeofenceReceiver`はデバウンス予約の可否に関わらず(タスクが見つからない/完了済み/通知タイミング未選択、いずれの場合も)ENTER/EXITイベントを受信するたびに1件記録し`detail`に理由を残すため、「イベント自体が来ていないのか」「来ているが条件で弾かれているのか」をlogcat無しでアプリ内(位置情報デバッグ画面)から切り分けられます。**`distanceMeters`/`radiusMeters`**は、そのイベントの`triggeringLocation`(タスクが見つからない・座標未登録なら`null`)からタスクに登録された座標までの距離とそのタスクの`radiusMeters`をそのまま記録したもので、例えば「距離8m/半径15m」のEXITであれば実際には圏内のままGPS/ネットワーク測位の誤差でEXITが誤検知されたと、`LocationDebugDialog`内の「更新履歴」セクション(`LocationUpdateLogRow`、距離・半径から「圏内」「圏外」も表示)から直接判別できます。距離計算自体は`LocationLookup.kt`のトップレベル関数`metersBetween()`(`android.location.Location.distanceBetween`のラッパー)に共通化しており、`GeofenceReceiver.distanceToTask`と`LocationDebugDialog`内の「現在地からの距離」表示の両方から使っています。ただし実際に通知したかどうかはこのログには残らず(`GeofenceConfirmWorker`がデバウンス確定後に通知履歴〈`NotificationLog`、`docs/architecture/notification-log.md`参照〉へ記録する)、`detail`が`"受信(3分後も継続していれば通知)"`のイベントがデバウンス中に反対方向のイベントで置き換えられた場合、そのまま通知されずに終わることがあります。加えて、`notification/LocationUpdateWorker`(`CoroutineWorker`)が`notification/LocationUpdateScheduler`経由で5分間隔の自己連鎖する`OneTimeWorkRequest`として動作し、位置情報を使う未完了タスクがある間だけ現在地を1回取得して`type = PERIODIC`で記録します(WorkManagerの`PeriodicWorkRequest`は最短でも15分間隔までしか指定できないため、より短い間隔で記録できるよう`LocationUpdateWorker`が実行完了のたびに`LocationUpdateScheduler.scheduleNext`〈`ExistingWorkPolicy.REPLACE`〉で次回分を予約する自己連鎖にしています。`LocationReminderManager.register`が位置情報タスクを登録するたびに`LocationUpdateScheduler.ensureScheduled`〈`ExistingWorkPolicy.KEEP`〉を呼んで連鎖を起動し、既に動作中なら何もしません。位置情報を使うタスクが無くなった場合は`LocationUpdateWorker`が次回分を予約せずに終わることで連鎖が自然に停止するため、停止までに最大5分の遅延があります。`PeriodicWorkRequest`と異なりWorkManagerが自動的に再実行してくれるわけではないため、`LocationUpdateWorker.doWork()`は位置情報タスクが残っている間の処理を`try`/`finally`で囲み、途中で例外が発生した場合でも必ず次回分を予約して連鎖が途切れないようにしています)。`LocationUpdateLogDao.insertAndTrim(log, retentionMillis)`(デフォルト6時間)が記録のたびに直近6時間より古い履歴を自動削除します。`TaskViewModel.locationUpdateLogs: StateFlow<List<LocationUpdateLog>>`(発生時刻の降順)として公開し、`LocationDebugDialog`内の「更新履歴」セクション(`LocationUpdateLogRow`)が新しい順に一覧表示します。バックアップのエクスポート/インポート対象には含めていません(通知履歴と同様、デバッグ用の実行時ログのため)。
