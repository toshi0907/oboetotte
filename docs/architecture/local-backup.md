# ローカルバックアップ(エクスポート/インポート)

**ローカルバックアップ(エクスポート/インポート)**: `app/src/main/java/com/toshi0907/oboetotte/backup/BackupManager.kt`が実体です。エクスポート形式はZIP(`oboetotte_backup_*.zip`)で、`backup.json`エントリに従来どおりのJSON構造(`{"version":2,"exportedAt":<epoch millis>,"lists":[...],"tasks":[...],"savedLocations":[...],"attachments":[...]}`。`lists`/`tasks`/`savedLocations`/`attachments`はそれぞれ`TaskList`/`Task`/`SavedLocation`/`TaskAttachment`の全フィールドをそのまま含む)、`attachments/<storedFileName>`エントリに添付ファイルの実体を格納します。インポート側は`org.json.JSONObject.isNull`がキー自体が存在しない場合も`true`を返す仕様を利用しており、`repeatDaysOfWeek`・`url`・`memo`・`seriesId`・`savedLocations`・`attachments`キーを含まない旧形式のバックアップファイルもエラーなく読み込めます。ZIPかどうかの判定はファイルの拡張子やMIMEタイプではなく、読み込んだバイト列先頭のZIPマジックナンバー(`PK\x03\x04`)を見て行っており(`BackupManager.isZip`)、添付機能追加前のプレーンJSON形式のファイルもそのまま読み込めます(標準ライブラリの`org.json`・`java.util.zip`のみを使用し、追加のシリアライズ用依存は入れていません)。`BackupManager.export(context, uri)`/`import(context, uri)`はいずれも`Dispatchers.IO`上で実行し、Roomの`taskListDao().getAll()`等を`Flow.first()`で1回だけ取得してZIPとして`ContentResolver`経由で書き出す/逆に読み込んでパースします。インポートは追記ではなく全置き換えです(`id`/`listId`/`parentTaskId`/`taskId`の対応関係を維持するため)。**インポートの安全性**: バックアップファイルは端末外で作られたZIP/JSONを信頼できない入力として扱い、既存データの削除より前に検証を済ませます。`AttachmentStorage.file()`はZIPエントリ名・JSON側の`storedFileName`のどちらについても単一ファイル名であること(パス区切りを含まない)と正規化後のパスが必ず`attachments`ディレクトリ直下に収まることを検証し、パストラバーサル(`../`等で`filesDir/attachments/`の外を指す値)を拒否します。また添付ファイルのメタデータ(JSON側の`attachments`配列)とZIPエントリの実体が過不足なく1対1で対応していることも検証し、一致しなければインポート全体を中断します。これらの検証をすべて通過した後、添付ファイルの実体をまず一時ディレクトリ(`filesDir/attachments_import_staging/`)へ書き込みます(ディスク容量不足等のI/O失敗はここで起きるため、失敗すれば既存のDB・添付ファイルには一切触れずに済みます)。全件の書き込みが成功した後、本来の`attachment/AttachmentStorage`のディレクトリを`filesDir/attachments_import_backup/`へ`renameTo`で退避し、一時ディレクトリを本来のディレクトリ名へ`renameTo`で入れ替えます(いずれもファイル単位ではなくディレクトリ単位の`renameTo`のみで、実体のコピーを伴わないため失敗の余地が小さい。`renameTo`は戻り値でしか失敗を通知しないため必ず確認し、失敗した場合は退避しておいたディレクトリを元の名前に戻します)。DBとファイルシステムは別々のリソースで単一のトランザクションにはできないため、**添付ディレクトリの入れ替えをDB更新より先に行う**順序にしており、`TaskDao`/`TaskListDao`/`SavedLocationDao`/`TaskAttachmentDao`の`deleteAll()`+`insertAll()`をRoomの`AppDatabase.withTransaction { }`でアトミックに置き換えるのは最後です。こうすることで、より失敗しやすいDB更新の方を最後にでき、DB更新が失敗した場合(Room側で自動的にロールバックされる)は直前で入れ替えたディレクトリも明示的に元へ戻します。これにより、検証・ファイル書き込み・ディレクトリの入れ替え・DB更新のいずれの段階で失敗しても、既存のDB・添付ファイルは基本的に元のまま残ります。UI側はメイン画面の「設定」`AssistChip`から遷移する設定画面(`SettingsScreen`、`MainActivity.kt`)の「バックアップ」セクションが導線で、実際のファイル選択は`MainActivity`に登録した`ActivityResultContracts.CreateDocument("application/zip")`(エクスポート)と`ActivityResultContracts.OpenDocument()`(インポート、mime `*/*`。上記の通り実際の形式判定は内容で行うため)というStorage Access Frameworkの標準コントラクトで行います。DAOの`getAll()`はRoomの`Flow`なので、インポート後の`deleteAll`/`insertAll`による変更も既存の`StateFlow`購読(`TaskViewModel`)へ自動的に反映され、画面の再起動は不要です。
