# リマインダー通知

**リマインダー通知**: `app/src/main/java/com/toshi0907/oboetotte/notification/`に`ReminderScheduler`(スケジュール/キャンセル)・`ReminderReceiver`(`BroadcastReceiver`、通知表示)・`BootReceiver`(端末再起動後の再スケジュール)を置いています。`ReminderScheduler.schedule(context, task)`は、`dueAt`が未来かつ`isDone == false`の場合に`AlarmManager.setExactAndAllowWhileIdle`でタスクIDを`PendingIntent`のリクエストコードとしたアラームを登録し、条件を満たさなければ`cancel`を呼びます。API 31(S)以降は`AlarmManager.canScheduleExactAlarms()`で正確なアラームの権限有無を確認し、無ければスケジュールをスキップします(`MainActivity`のバナーから`Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM`で設定画面へ誘導)。`TaskViewModel`の`updateTask`・`toggleDone`(繰り返しタスクの次回生成分を含む)・`deleteTask`からこの`schedule`/`cancel`を呼び出し、常にDBの状態とアラームの登録状態を同期させています。`ReminderReceiver`は発火時にRoomから最新のタスク情報を`taskDao.getById`で取得し直し(タイトル変更や削除に追従)、未完了であれば通知チャンネル`task_reminders`で通知を表示します。`BootReceiver`は`RECEIVE_BOOT_COMPLETED`を受けて`taskDao.getPendingWithDueDate()`の全件を再スケジュールします。API 33(TIRAMISU)以降は`POST_NOTIFICATIONS`権限が必要なため、`MainActivity.onCreate`で未許可なら都度リクエストしています。設定画面(`SettingsScreen`)の「テスト通知」ボタンからは`ReminderScheduler.scheduleTestNotification(context)`を呼び出し、タスクに紐づかない実際のアラーム経路(`TEST_DELAY_SECONDS`=5秒後、`ReminderReceiver`が`EXTRA_IS_TEST`フラグを見てDB参照無しで固定文言の通知を表示)を使って通知が届くかどうかを、本番と同じ経路のまま検証できます。**スヌーズ**: Androidの通知は表示できるアクションボタンが実質最大3個程度に制限されており(それ以上`addAction`しても通知欄には表示されないだけで、明示的なエラーにはならない)、以前は`ReminderScheduler.SNOOZE_OPTIONS`(15分後/30分後/1時間後/3時間後/1日後)の5件をボタンとして直接並べていたため、「完了」やURLの「リンクを開く」ボタンと合わせた際に一部のボタンが表示されない不具合があった。これを解消するため、タスクの通知(テスト通知は対象外)には「スヌーズ」ボタンを1つだけ付与しており、タップすると`notification/SnoozePickerActivity`(`Theme.Oboetotte.SnoozeDialog`でウィンドウ自体を透過にし、Compose側の`AlertDialog`だけを表示する専用Activity)が起動します。ダイアログで`SNOOZE_OPTIONS`のいずれかを選んだ時点で現在の通知(`NOTIFICATION_TAG_DUE`)を消去し、`ReminderScheduler.scheduleSnooze(context, taskId, minutes)`で「タップ時刻+選択した分数」後に再度アラームを発火させて`finish()`します(何も選ばず「キャンセル」や外側タップで閉じた場合は通知に触れないため、元のリマインダー通知がそのまま残ります)。**タスクの`dueAt`自体は変更しません**(スヌーズは通知タイミングだけをずらすもので、期限の再設定ではないため)。`scheduleSnooze`はアラーム本体(`schedule`/`cancel`)と同じ`pendingIntentFor`(リクエストコード=`taskId.toInt()`、`ReminderReceiver`宛)を再利用して発火時刻だけを書き換えているので、後から`updateTask`等で`schedule`/`cancel`が呼ばれれば通常どおり上書き・キャンセルされます。「スヌーズ」ボタン自身の`PendingIntent`(`snoozePickerPendingIntent`、`SnoozePickerActivity`宛)は`taskId.toInt() * 10 + 5`をリクエストコードとして使います。**オートスヌーズ**: `Task.autoSnoozeMinutes`(任意、`SNOOZE_OPTIONS`と同じ分数のいずれか)をタスクごとに設定しておくと、`ReminderReceiver`が期限日時通知(通常発火・手動スヌーズ・オートスヌーズいずれの経路でも)を表示した直後、そのタスクが未完了であれば`ReminderScheduler.scheduleAutoSnooze(context, taskId, minutes)`で「表示時刻+`autoSnoozeMinutes`分後」に次のアラームを予約し、完了するまで上限なく再通知を繰り返します。このアラームは`pendingIntentFor`が組み立てる同じ`PendingIntent`(taskIdをリクエストコードとする枠、`EXTRA_IS_AUTO_SNOOZE`で識別)を`schedule`/`scheduleSnooze`と共有しているため、手動で「スヌーズ」を選ぶとその時刻を基準に次回のオートスヌーズが計算し直され(手動スヌーズが優先)、`dueAt`の変更やタスク完了による`schedule`/`cancel`が呼ばれれば通常どおり上書き・キャンセルされます。`schedule`は`dueAt`が過去(期限到達後)の場合、通常は通知済みとみなしキャンセルするだけですが、`autoSnoozeMinutes`が設定された未完了タスクに限りキャンセルせず「今から指定間隔後」を基準にオートスヌーズを立て直します(端末再起動時の`BootReceiver`の再スケジュールや、期限日時を変えずに他の項目だけを編集した`updateTask`経由の呼び出しのたびに、進行中のオートスヌーズが理由なく止まってしまうことを避けるため)。通知履歴(`NotificationLog`)の`triggerCondition`には手動スヌーズ経由と区別して「オートスヌーズ経由の再通知」と記録され、AI要約(`docs/architecture/ai-gemini.md`参照)はオートスヌーズ経由でも手動スヌーズと同様に`aiCachedResponse`を再利用しAPIは再呼び出ししません。`EditTaskDialog`の「繰り返し」直下、`TaskDetailDialog`にそれぞれ設定・表示できます。**通知のみタスク**: `Task.notifyOnlyMode`(タスクごとに個別設定、既定`false`)を有効にすると、通知されること自体が重要でタスク完了の確認が不要なタスク向けに、期限日時通知(位置情報通知は対象外)を実際に表示できた時点で`ReminderReceiver`が`TaskCompletion.complete(context, task)`を呼び自動的に完了にします(繰り返しタスクならそのまま次回分が生成・スケジュールされる)。`NotificationManagerCompat.notify`が権限不足等で呼べず通知を実際には表示できなかった場合は完了させません(通知されないままタスクが消えてしまうことを避けるため、`showNotification`の戻り値`posted`を見てから完了処理を行う)。この機能は「スヌーズ機能は使わない」仕様のため、通知には「完了」「スヌーズ」ボタンをいずれも付与せず(`showTaskActions = false`相当)、`autoSnoozeMinutes`とは併用しません。`TaskViewModel.updateTask`は`edits.notifyOnlyMode`が`true`の場合に`autoSnoozeMinutes`を強制的に`null`へ正規化し(`EditTaskDialog`側もこの条件下ではオートスヌーズの選択UI自体を表示しません)、両者が同時に有効な状態にならないようにしています。通知履歴の`triggerCondition`には「(通知のみ・自動完了)」が付記されます。`EditTaskDialog`の「繰り返し」直下、`TaskDetailDialog`にそれぞれ設定・表示できます。この自動完了経路の追加により、同じタスクに対して`ReminderReceiver`(自動完了)とアプリ内のチェックボックス/通知の「完了」ボタン(手動完了)がほぼ同時に`TaskCompletion.complete`を呼ぶ競合が従来より起きやすくなったため、`TaskDao.setDone(taskId, isDone)`は`WHERE id = :taskId AND isDone != :isDone`という条件で実際に状態遷移した行数(`Int`)を返すようにしており、`TaskCompletion.complete`はこれが`0`件(=既に他方の呼び出しが完了させていた)であれば繰り返しタスクの次回分生成を行わずに早期returnします(渡された`task`スナップショットの`isDone`は呼び出し時点で古い可能性があるため、判定はDBへの書き込み結果そのものを見て行う)。**完了ボタン**: タスクの通知には「完了」ボタンも付与しており、タップすると`notification/CompleteReceiver`が起動します。期限日時通知(`ReminderReceiver`)の「完了」ボタンは`completePendingIntent`(`CompleteReceiver`宛・リクエストコード`taskId.toInt()`)を使い、通知を表示した時点の`task.dueAt`を第3引数(`ReminderScheduler.EXTRA_DUE_AT`としてIntentへ載る)に渡します。位置情報通知(`LocationReminderNotifier`)の「完了」ボタンは期限の概念が無いため別の`locationCompletePendingIntent`(`CompleteReceiver`宛・同じくリクエストコード`taskId.toInt()`)を使い、`EXTRA_DUE_AT`を載せません。この2つは`taskId.toInt()`というリクエストコードは同じですが、Intentの`action`をそれぞれ`ACTION_COMPLETE_DUE`/`ACTION_COMPLETE_LOCATION`という別の文字列にすることで別々の`PendingIntent`として区別しています(`PendingIntent`の同一性はコンポーネント・リクエストコード・Intentの`action`/`data`/`categories`/型で決まり、extrasの違いは同一性に影響しないため、actionを分けないと`FLAG_UPDATE_CURRENT`により後から作られた側の`EXTRA_DUE_AT`の有無で、もう片方の既に表示済みの通知に埋め込まれたPendingIntentの中身まで上書きされてしまう。また、`taskId.toInt() * 10 + N`のようにリクエストコードだけをずらす方式では、`taskIdA == taskIdB * 10 + N`となる別タスク同士のリクエストコードが偶然一致する可能性を防げないため採用していません)。`CompleteReceiver`はタップされた通知自身のタグ(期限日時通知経由なら`NOTIFICATION_TAG_DUE`、位置情報通知経由なら`NOTIFICATION_TAG_LOCATION`)だけをまず`cancel`し(期限不一致で完了させない場合でもタップされた通知自体は古いので消してよいが、まだ有効なもう片方のタグの通知までは消さない)、その上で期限日時通知(`EXTRA_DUE_AT`付き)であれば完了処理直前に読み直したタスクの現在の`dueAt`と一致する場合のみ、位置情報通知(`EXTRA_DUE_AT`無し)であれば従来通りタスクが存在すれば、`TaskCompletion.complete(context, task)`(アプリ内のチェックボックスから完了にする場合と同じ共通処理。繰り返しタスクなら次回分の生成・スケジュールも行う)を呼びます。`dueAt`の突き合わせは、繰り返しタスクをアプリ内で先に完了させた後(次回分は別IDの新規タスクとして生成されるため、通常はこの古い通知の「完了」を押しても対象は変わらず無効化されるだけですが)、`dueAt`の変更を伴う編集が同じタスクIDに対して行われた場合等に、表示時点とは異なる期限のタスクを誤って完了させないための安全策です。また、通知の「完了」ボタン経由に限らず、アプリ内のチェックボックスや「通知のみタスク」の自動完了など`TaskCompletion.complete`のどの呼び出し経路でも、その時点で表示中のそのタスクの通知(期限日時・位置情報の両タグ)を`complete`関数の先頭で消去するため、通知を経由せず完了させた場合に古い通知が通知欄に残り続けることはありません。**通知タグ**: `ReminderReceiver`(期限日時)は`ReminderScheduler.NOTIFICATION_TAG_DUE`、`GeofenceReceiver`(位置情報、`docs/architecture/location-reminders.md`参照)は`NOTIFICATION_TAG_LOCATION`という別々のタグを付けて`NotificationManagerCompat.notify(tag, id, ...)`しています(通知ID自体は「完了」ボタンの消去用途のため両方`taskId.toInt()`で揃えていますが、`notify`の実体は`(タグ, ID)`の組で識別されるため、同じタスクに期限日時・位置情報の両方のリマインダーを設定していて両方が発火した場合でも、タグが異なることで片方がもう片方を通知欄から消してしまうことなく両方とも表示されます)。`CompleteReceiver`は両方のタグを`cancel`してタスク完了時にどちらの通知も消し、`SnoozePickerActivity`(スヌーズボタンは期限日時通知にのみ付く)はスヌーズ時間の選択確定時に`NOTIFICATION_TAG_DUE`のみを`cancel`します。
