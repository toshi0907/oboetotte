# クラウド自動バックアップ

**クラウド自動バックアップ**: 上記のローカルバックアップとは別に、Storage Access Framework(SAF)で選択したフォルダへ毎日1回自動でZIPバックアップする機能です。Dropbox・Google Drive・OneDrive等、SAFのドキュメントプロバイダとして自身を公開しているクラウドストレージアプリがインストールされていれば、標準のフォルダ選択ダイアログからそのアプリ内のフォルダを保存先に選べるため、Dropbox APIのようなアプリ固有のAPIキー取得・OAuth認証の実装は一切不要です(選んだフォルダへの書き込みは、そのフォルダを提供しているアプリ自身がクラウドへの同期を担います)。`backup/CloudBackupSettings`(SharedPreferences`cloud_backup_settings`。有効/無効・保存先フォルダのツリーURI・保持件数〈`MIN_RETENTION_COUNT`=1〜`MAX_RETENTION_COUNT`=90、既定`DEFAULT_RETENTION_COUNT`=7〉・保存時刻〈時・分、既定`DEFAULT_BACKUP_HOUR`=3時`DEFAULT_BACKUP_MINUTE`=0分〉・最終実行時刻/結果〈`CloudBackupResult`の`SUCCESS`/`FAILURE`〉を永続化)、`backup/CloudBackupRunner.run(context)`(実処理。`BackupManager.export`と同じ内容のZIPをまず端末内の一時ファイル〈`context.cacheDir`〉へ書き出し、これが成功した場合のみ保持件数-1件になるまで古いファイルを`pruneOldBackups`で削除し、日時付きファイル名`oboetotte_cloud_backup_*.zip`で`DocumentFile.createFile()`により保存先フォルダへ新規作成した上でその一時ファイルの内容をコピーし、結果を`CloudBackupSettings.recordResult`へ記録する。この順序〈エクスポート成功の確認→古いファイルの削除→保存先への作成・コピー〉には2つの意図がある。まず、新規ファイルの作成・書き込みを先に行い削除を後回しにすると、保持件数ちょうどの状態から次のバックアップを取る際に一時的に保持件数+1件分の保存領域が必要になり、保存先の空き容量やクォータが保持件数ちょうどしか無い場合〈保持件数の上限に達している場合〉に失敗してしまう。一方、古いファイルの削除をZIPの書き出し(DBの読み込み・ZIP生成、端末のローカルストレージのみを使うため保存先フォルダの空き容量・クォータには影響しない)の成否が分かる前に行うと、書き出し自体が失敗した際に古いバックアップを削除しただけで新しいものが用意できず、既存のバックアップを失ってしまう。ZIPの書き出しを先に済ませ、それが確実に成功した後にだけ保存先フォルダの古いファイルを削除することで、この失敗パターンは避けている(なお、削除後の保存先への新規ファイル作成・コピー自体がネットワークエラー等で失敗した場合は、その回に限り保持件数より1件少ない状態になりうるが、これは保存先の容量が保持件数ちょうどしか無い状況で新規ファイルを追加する以上、原理的に避けられないトレードオフである)。ローカルバックアップの手動エクスポート〈`docs/architecture/local-backup.md`参照、ファイル名`oboetotte_backup_*.zip`〉と意図的に異なるプレフィックスにしており、ユーザーが手動エクスポートの保存先として同じクラウドフォルダを選んでも、保持件数超過分の削除〈`pruneOldBackups`〉が手動エクスポートしたファイルを巻き込んで削除してしまわないようにしている)、`backup/CloudBackupWorker`(`CoroutineWorker`。`backup/CloudBackupScheduler`が`PeriodicWorkRequest`で24時間間隔にスケジュールし、`CloudBackupRunner.run`を呼ぶだけ。保存先はDropbox等のアプリ自身が同期を担うためネットワーク接続を制約条件にしていません)で構成されています。設定画面(`SettingsScreen`)の「クラウド自動バックアップ」セクションから、`ActivityResultContracts.OpenDocumentTree()`(`MainActivity`の`selectCloudBackupFolderLauncher`)でフォルダを選択すると`TaskViewModel.setCloudBackupFolder(uri)`が`ContentResolver.takePersistableUriPermission()`で書き込み権限を永続化してから保存し(アプリ・端末の再起動を越えて有効)、`FilterChip`で自動バックアップの有効/無効を切り替えられます(有効化は保存先フォルダが未設定だと`TaskViewModel.setCloudBackupEnabled`内で無視されます)。有効化は`CloudBackupScheduler.reschedule`、無効化は`cancel`を呼びます。`reschedule`(`ExistingPeriodicWorkPolicy.REPLACE`)は現在の保存時刻設定(`CloudBackupSettings.getBackupHour`/`getBackupMinute`)から「次に訪れるその時刻」までの遅延を計算し、`PeriodicWorkRequest`の初回遅延として指定し直すことで、既存の定期実行があってもその場で新しい時刻に合わせて再登録します(WorkManagerの定期実行は正確なアラームではないため、実際の発火時刻は多少前後します)。設定画面の「変更」ボタンから`TimePicker`(`AlertDialog`+`rememberTimePickerState`、期限日時の時刻選択と同じ部品)で保存時刻を選ぶと`TaskViewModel.setCloudBackupTime(hour, minute)`が設定を保存し、自動バックアップが有効化中であれば同じ`reschedule`を呼んで次回実行時刻に即座に反映します(無効化中は設定を保存するだけで、実際のスケジュール登録は次回有効化時に行われます)。`MainActivity`は起動のたびに`CloudBackupScheduler.ensureScheduled`(`ExistingPeriodicWorkPolicy.KEEP`)を呼び、(有効かつ保存先設定済みなのに)定期実行が何らかの理由で登録されていない場合にのみ現在の保存時刻設定で新規登録します(`AppUpdateCheckScheduler`と同様の保険的パターンで、既存の定期実行がある限り初回遅延は再計算されません)。「今すぐバックアップ」ボタンから`TaskViewModel.runCloudBackupNow`で定期実行と同じ処理を即座に1回行え、直近の実行結果(成功/失敗・実行時刻)も同じ画面に表示されます。`cloudBackupLastBackupAt`/`cloudBackupLastResult`は`CloudBackupSettings.recordResult`によるSharedPreferencesの変更を`SharedPreferences.OnSharedPreferenceChangeListener`(`TaskViewModel`の`init`で`CloudBackupSettings.addLastResultChangeListener`により登録、`onCleared`で解除)で直接購読して同期しており、`CloudBackupWorker`による定期実行の結果もアプリのプロセスが生きている間はアプリを再起動せず即座に画面へ反映されます(SharedPreferencesはリスナーをWeakReferenceでしか保持しないため、`TaskViewModel`側でリスナーをフィールドとして保持し続けています)。バックアップの対象データ・ZIP形式はローカルバックアップと完全に同一(`BackupManager.export`をそのまま再利用)で、復元(インポート)は引き続きローカルのZIPファイル選択(`docs/architecture/local-backup.md`の`importBackupLauncher`)からのみ行う想定です(クラウド上のファイルであっても、端末のファイル選択ダイアログから選べば同じ`BackupManager.import`でインポートできます)。
