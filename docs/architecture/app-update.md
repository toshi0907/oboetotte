# アプリ内アップデート

**アプリ内アップデート**: `app/src/main/java/com/toshi0907/oboetotte/update/`(`AppUpdateChecker`/`AppUpdateInstaller`/`AppUpdateNotifier`/`AppUpdateCheckSettings`)が実体です。Google Playを使わず`latest-debug`タグ(CLAUDE.mdのCI/ビルドパイプライン参照)経由で配布しているため、Play Coreのアプリ内アップデートAPIは使えません。`versionCode`/`versionName`も固定値(`app/build.gradle.kts`、1/"1.0")で、CIが`main`への毎pushで`latest-debug`タグのAPKを上書きするだけのため、バージョン番号での新旧比較ができません。ビルド時にgitのコミットSHAを`BuildConfig.GIT_COMMIT_SHA`として埋め込む(`app/build.gradle.kts`内の`resolveGitCommitSha()`。GitHub Actions上のビルドでは自動設定される環境変数`GITHUB_SHA`を使い、無ければ`git rev-parse HEAD`にフォールバック、いずれも失敗すれば`"unknown"`。設定画面に現在のビルドを表示する用途にのみ使う)のに加えて、新旧判定には単調増加する**ビルド番号**を使います。コミットSHA同士は「等しいか」しか分からず順序を比較できないため(ローカルビルドのSHAが`latest-debug`と異なるだけで「新しい」と誤判定しうる)、GitHub Actions上のビルドでは実行のたびに増加する環境変数`GITHUB_RUN_NUMBER`を`resolveBuildNumber()`で読み取り`BuildConfig.BUILD_NUMBER`として埋め込みます(ローカルビルド等`GITHUB_RUN_NUMBER`が無い環境では`0`)。`latest-debug`リリースの本文にも同じ値を`ビルド番号: <n>`(`.github/workflows/android-build.yml`の`${{ github.run_number }}`)として埋め込んでおり、これと`BuildConfig.BUILD_NUMBER`を比較します。**`AppUpdateChecker.check()`**(ブロッキングI/O、呼び出し元が`Dispatchers.IO`上で呼ぶ想定は`attachment/AttachmentStorage`と同じ方針)は、GitHub API(`https://api.github.com/repos/.../releases/tags/latest-debug`、publicリポジトリのため認証不要。User-Agentヘッダ必須)を`java.net.HttpURLConnection`+`org.json`(いずれも標準ライブラリ、追加の依存無し)で叩き、レスポンスJSONの`body`から正規表現でビルド番号を抽出し、`BuildConfig.BUILD_NUMBER`(`0`以下なら判定不能として`CheckFailed`)より大きい場合のみ「更新あり」と判定します。結果は`sealed interface Result`(`UpdateAvailable(downloadUrl, buildNumber)`/`UpToDate`/`CheckFailed`〈ビルド番号が判定できない場合や通信エラー・パース失敗を含む〉)で返します。`MainActivity`の`setContent`内で`LaunchedEffect(Unit)`により起動のたびに自動チェックし(`updateCheckResult`としてComposeの状態に保持)、`TaskScreen`は`UpdateAvailable`の場合のみ既存の権限バナーと同じ見た目(`Card`+`TextButton`、ただし`primaryContainer`色でエラーではなく通常の通知として区別)で更新バナーを表示、`SettingsScreen`の「アップデート」セクションは結果の種類に応じたテキストと「更新を確認」ボタン(`onCheckForUpdate`で再チェック)を常時表示します。**最終確認時刻**: `AppUpdateChecker.check()`を呼ぶたび(起動時の自動チェック・「更新を確認」ボタン・後述のバックグラウンド定期チェックのいずれも)に`AppUpdateCheckSettings.recordCheckedAt(context, millis)`でSharedPreferences`app_update_check_settings`へ記録し、`SettingsScreen`の「アップデート」セクションに「最終確認: <日時>」として表示します。`TaskViewModel.updateLastCheckedAt`(`StateFlow<Long?>`)は初期値を`AppUpdateCheckSettings.getLastCheckedAt`から読み込みつつ、`backup/CloudBackupSettings.addLastResultChangeListener`と同じ考え方の`SharedPreferences.OnSharedPreferenceChangeListener`(`init`で登録・`onCleared`で解除)でSharedPreferences側の変更を直接購読するため、アプリを開いたままバックグラウンドの定期チェック(`AppUpdateCheckWorker`)が実行された場合もアプリ再起動無しに画面へ反映されます。**ダウンロード中の表示**: APKのダウンロード自体に時間がかかりインストールダイアログが出るまでボタンを押せたかどうか分かりづらかったため、`MainActivity`の`downloadAndInstallUpdate()`はダウンロード開始から完了(成功・失敗いずれも`finally`で解除)まで`isDownloadingUpdate`(Composeの状態)を`true`にし、`TaskScreen`のバナー・`SettingsScreen`の「ダウンロードしてインストール」ボタン双方でこの間ボタンを無効化しラベルを「ダウンロード中…」に変えます。**インストール**: `AppUpdateInstaller.download(context, url)`(同じくブロッキングI/O)が`filesDir/updates/`配下にAPKをダウンロードし、`hasInstallPermission(context)`(`PackageManager.canRequestPackageInstalls()`、API 26以降必須)が`false`なら`unknownSourcesSettingsIntent()`(`Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES`)で設定画面へ誘導、`true`なら`installIntent(context, file)`(`attachment/AttachmentStorage.openIntent`と同様`FileProvider`経由、`res/xml/file_paths.xml`に`updates/`を追加)で`ACTION_VIEW`+`application/vnd.android.package-archive`のIntentを起動しシステムのパッケージインストーラーにインストール確認を委ねます(自動インストールはできないため、ユーザーの最終確認は必ず挟まります)。`AndroidManifest.xml`に`INTERNET`・`REQUEST_INSTALL_PACKAGES`権限を追加しています。**バックグラウンドでの定期チェック**: アプリを開いていない間も新しいビルドに気づけるよう、`AppUpdateCheckScheduler`(`notification/LocationUpdateScheduler`と同様の構成)がWorkManagerの定期ジョブ`AppUpdateCheckWorker`(`CoroutineWorker`)を6時間間隔(`NetworkType.CONNECTED`制約付き。接続が無いタイミングではWorkManager側が復帰まで実行を保留する)でスケジュールします。`MainActivity`が起動のたびに`ensureScheduled`を呼びますが`ExistingPeriodicWorkPolicy.KEEP`のため既に動作中なら何もせず、位置情報の定期取得とは異なり常時有効な機能のため動的に停止する仕組みは持ちません。`AppUpdateCheckWorker`は`AppUpdateChecker.check()`を呼び、`UpdateAvailable`かつ`AppUpdateNotifier.shouldNotify(context, buildNumber)`(SharedPreferences`app_update_notifier`に記録した最後に通知したビルド番号と比較し、同じビルドに対して繰り返し通知しない)が`true`の場合のみ`AppUpdateNotifier.showNotification`で通知チャンネル`app_updates`の通知(タップでアプリを開くのみ。`notification/LocationReminderNotifier`と同様の組み立て)を表示します。`showNotification`は`NotificationManagerCompat.areNotificationsEnabled()`とチャンネルの`importance`(`IMPORTANCE_NONE`でないか)を`notify()`の直前に確認し、いずれかでブロックされていれば通知もSharedPreferencesへの記録も行わずに`false`を返します(通知がブロックされている間に記録だけ進んでしまうと、後でユーザーが通知を許可し直しても同じビルドについて二度と通知されなくなるため)。
