# 期限ピッカー・DBマイグレーション

期限は`DatePickerDialog`+`TimePicker`(いずれも`@ExperimentalMaterial3Api`)を連続で開いて設定・クリアでき、`DatePicker`が返す`selectedDateMillis`はUTC 0時のepoch millisなので、選択した時刻と合成する際は`combineDateAndTime()`(`MainActivity.kt`内のプライベート関数)でローカルタイムゾーンに変換しています。`EditTaskDialog`の「設定」ボタンをタップして期限ピッカーを開いた時点でまだ期限(`dueAt`)が未設定の場合、`DatePicker`の初期選択日は`todayAsDatePickerMillis()`(端末のローカルタイムゾーンでの「今日」をUTC 0時基準のepoch millisに変換するプライベート関数)、`TimePicker`の初期時刻は`LocalTime.now()`となり、いずれも現在日時がデフォルト表示されます(既に`dueAt`が設定済みの場合は、その日時をそのまま初期値として表示します)。この挙動はタスク追加時のデフォルト値(`TaskViewModel.addTask`/`addSubtask`が設定する登録時刻の1時間後、`docs/architecture/task-viewmodel.md`参照)とは無関係です。**期限のクイック選択**: 「設定」/「クリア」ボタンの下に`DUE_QUICK_OPTIONS`(`MainActivity.kt`内、ラベルと「タップ時点の現在時刻(epoch millis)→期限(epoch millis)」を計算する関数`(Long) -> Long`のペアのリスト。5分後/15分後/30分後/1時間後/3時間後/6時間後/1日後/1週間後/1ヶ月後)ぶんの`AssistChip`を並べており、タップすると`dueAt`に計算結果を直接セットします(カレンダー/時刻ピッカーを介さない簡易入力)。日・週は固定長のため`addMinutes()`で分加算するだけですが、月は日数が28〜31日と変動するため`addMonths()`で`java.time`の`plusMonths(1)`によるカレンダー月単位の加算を行います(`TaskCompletion.nextDueAt`の繰り返しタスクの月加算と同じ考え方)。`DUE_QUICK_OPTIONS`のチップの前には「当日朝/昼/夕/夜」のチップ(`DueTimeSlot`、`DueTimePresets.kt`)を並べており、タップするとタップ時点の端末ローカル日付+設定時刻(`todayAtMinuteOfDay()`)を`dueAt`にセットします。各時刻は`DueTimePresetSettings`(SharedPreferences、0時からの分数で保存。既定は7:00/12:00/17:00/20:00、時間帯同士の前後関係は検証しない)に保存し、設定画面の「期限のクイック選択」セクションで変更します(`TaskViewModel.dueTimePresets`/`setDueTimePreset`)。`EditTaskDialog`はダイアログを開いた時点で`DueTimePresetSettings.getAll()`を直接読み込みます(呼び出し箇所が多く引数を引き回さないため)。既に時刻を過ぎた時間帯のチップは、過去日時を設定して即通知されないよう無効化(onClick側でも再判定)します。「当日」チップの後ろには同じ設定時刻を使う「明日の朝/昼/夕/夜」のチップを並べており、タップ時点の翌日の日付+設定時刻(`tomorrowAtMinuteOfDay()`)をセットします(常に未来日時のため無効化はしません)。チップは「当日」「明日」「`DUE_QUICK_OPTIONS`(5分後〜1ヶ月後)」の3グループをそれぞれ別の`LazyRow`(1グループ1行、幅が足りない場合は行ごとに横スクロール)に分けて縦に3行で表示します。この時刻設定はバックアップ(ZIP)の対象外です。他の項目と同様にダイアログ内の状態を書き換えるだけで、「保存」ボタンを押すまでDBには反映されません。**DBマイグレーション**: `AppDatabase`はバージョン6以降、明示的な`Migration`オブジェクト(`MIGRATION_6_7`〜`MIGRATION_10_11`、`AppDatabase.kt`内の`companion object`に定義)で`ALTER TABLE`/`CREATE TABLE`のSQLを直接実行し、アプリ更新時に端末内のデータを保持したままスキーマを更新します(以前は`fallbackToDestructiveMigration()`のみでデータが破棄されていましたが、実運用でのデータ消失が問題になったため導入しました)。**エンティティのスキーマを変更する際は、`@Database`の`version`を上げるのに加えて、必ず新しいバージョンへの`Migration`を追加し`addMigrations()`に登録してください。** 追加を怠ると、そのバージョン間で更新したユーザーのデータが失われます。`fallbackToDestructiveMigration()`は、対応する`Migration`が定義されていない古いバージョン(6より前)からの更新時のみ働く最終手段として残しています。
