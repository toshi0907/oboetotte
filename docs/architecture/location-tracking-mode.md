# 位置情報リマインダーの確認方式(連続追跡)

**位置情報リマインダーの確認方式**: Geofencing APIは内部の評価間隔を端末側で間引くことがあり、実際には数時間前に起きていた遷移がまとめて(複数タスク同時に)遅れて通知される「遅延キャッチアップ」が起こりうるため、これを避けたいユーザー向けに、Geofencing APIとは別のもう1つの確認方式として**連続追跡方式**を選択できます。`notification/LocationTrackingMode`(`GEOFENCING_API`/`CONTINUOUS_TRACKING`)と`notification/LocationTrackingSettings`(SharedPreferences`location_tracking_settings`。モードと更新間隔〈分、`MIN_INTERVAL_MINUTES`=1〜`MAX_INTERVAL_MINUTES`=60、既定`DEFAULT_INTERVAL_MINUTES`=15に丸める〉を永続化)で表し、アプリ全体で共通の設定です(タスクごとの個別設定ではありません)。設定画面(`SettingsScreen`)の「位置情報」セクションで`FilterChip`による方式選択と、連続追跡方式選択時のみ表示される更新間隔の入力欄(分、保存ボタンで確定)を提供します。`notification/LocationReminderManager`の`register`/`unregister`は`LocationTrackingSettings.getMode`で分岐し、Geofencing APIモードでは従来どおりジオフェンスを登録する一方、連続追跡方式では`notification/LocationTrackingService`(フォアグラウンドサービス、`android:foregroundServiceType="location"`、`FOREGROUND_SERVICE`・`FOREGROUND_SERVICE_LOCATION`権限が必要)を起動します。`LocationTrackingService`は`FusedLocationProviderClient.requestLocationUpdates`で設定した間隔を希望値として位置の更新を要求し(`LocationRequest.Builder`の`intervalMillis`/`setMinUpdateIntervalMillis`。端末やシステムの状態によっては実際の更新がそれより遅れることがあります)、`taskDao.getPendingWithLocation()`の全件それぞれについて`metersBetween()`で距離を計算し圏内/圏外を判定、前回評価時の状態を`data/GeofenceState`(`taskId`/`isInside`/`latitude`/`longitude`/`radiusMeters`、`AppDatabase`バージョン15→16の`MIGRATION_15_16`で追加した`geofence_states`テーブル。プロセス再起動を挟んでも基準を見失わないようRoomに永続化)と比較して遷移を検知します(初回評価時はGeofencing APIの`INITIAL_TRIGGER_ENTER`と同様、既に圏内かつ到着通知希望の場合のみ即座に扱う)。`latitude`/`longitude`/`radiusMeters`は、記録した`isInside`がどのジオフェンス定義(位置・半径)に基づく評価結果かを表す。`LocationReminderManager.register`はタスクの編集(位置・半径と無関係な項目の変更を含む)のたびに呼ばれるため、記録済みの定義がタスクの現在の設定と一致する場合は基準値をそのまま保持し(無駄な初回評価扱いによる到着通知の再送を避ける)、位置・半径が実際に変わった場合のみ削除して次回評価を初回評価扱いにする。`LocationTrackingService.evaluateTask`側でも同様の一致確認を行い、万一削除し損ねた基準値が残っていても誤判定しないようにしている。遷移を検知した後の処理はGeofencing APIモードと共通で、`GeofenceReceiver`と同じ`GeofenceConfirmWorker.schedule()`(3分デバウンス)に合流させ、位置情報の更新履歴(`docs/architecture/location-update-log.md`参照)にも`〈連続追跡〉`のdetail付きで記録します。`LocationReminderManager.switchMode(context, newMode)`は方式切り替え時に旧方式のリソース(Geofencing APIなら共有`PendingIntent`単位での全ジオフェンス一括解除、連続追跡方式ならサービス停止+`geofence_states`全削除)を解除してから新方式で`reconcileAll`(位置情報を使う未完了タスクの再登録)を行い、`updateContinuousTrackingInterval(context, minutes)`は間隔変更時にサービスが動作中であれば再起動して即座に新間隔を反映します。`BootReceiver`は引き続き`LocationReminderManager.register`経由で呼ぶため、モードを意識せず端末再起動後の再登録が両方式に対応します。**排他制御**: `register`/`unregister`/`switchMode`/`reconcileAll`/`updateContinuousTrackingInterval`はいずれも`LocationReminderManager`が持つ単一の`Mutex`で直列化しています。これらは複数の独立したコルーチン(`TaskViewModel`の各操作・`BootReceiver`・設定画面からの確認方式/更新頻度変更)から並行に呼ばれうるため、直列化しないと例えば確認方式の切り替え中に古い`updateContinuousTrackingInterval`呼び出しが完了して停止直後のサービスを再起動してしまう、といった順序崩れが起こりえます。内部的には各公開関数がロックを取得したうえで`registerLocked`等の非公開実装に委譲し、`reconcileAll`から`register`を呼ぶ場合のように関数間で連鎖する処理は非公開実装同士を直接呼び合うことで同じロックの二重取得(デッドロック)を避けています。Geofencing APIモードの`addGeofences`/`removeGeofences`はPlay services側で非同期の`Task`を返すため、`registerGeofencingApi`/`unregisterLocked`/`switchMode`はいずれも`awaitCompletion()`(`suspendCancellableCoroutine`+`addOnCompleteListener`によるブロッキングしない待ち合わせ)でその完了までロックを保持し続けます。これを怠ると、例えば確認方式をGeofencing API→連続追跡→Geofencing APIと短時間で往復させた際に、最初の解除処理の完了が2回目の再登録より後になり、せっかく登録し直したジオフェンスを消してしまうことがあるためです。`awaitCompletion()`自体は`withContext(NonCancellable)`で包み、呼び出し元のコルーチン(`TaskViewModel.viewModelScope`や`MainActivity`の`rememberCoroutineScope`)が途中でキャンセルされてもこの待ち合わせ(=ロックの保持)だけは中断されないようにしています(そうしないと発行済みのTaskが完了しないままロックだけ解放され、直列化が崩れるため)。また`LocationTrackingService`は`onLocationResult`から直接評価用コルーチンを起動するのではなく、`Channel<Location>`(`CONFLATED`。評価〈Room読み書き・ワーカー予約・ログ書き込みを含む〉が設定間隔より時間がかかってコンシューマーが遅れても、未処理の位置情報が無制限に溜まり続けないよう、最新の1件のみ保持し古いものは破棄する)に`trySend()`で積むだけに留め、`onCreate`で1つだけ起動する単一のコンシューマーコルーチンが順に`for (location in locationChannel)`で取り出して評価します(`scope.launch`を毎回呼ぶ方式だと、コルーチンの起動自体は非同期なため開始順序がコールバックの到着順と入れ替わりうるが、`trySend`は同期的にキューへ積むだけなので到着順がそのまま処理順になる)。このコンシューマーは`SupervisorJob`配下で動作しますが、`handleLocation`(Room操作・`GeofenceConfirmWorker.schedule`等を含む)が`CancellationException`以外の例外を投げた場合にループ自体を抜けて終了してしまうと、`SupervisorJob`のおかげで親の`scope`は無事でもこのコンシューマー自身は二度と再開せず、以後受信する位置情報が一切評価されなくなってしまいます。これを避けるため、`for`ループ内で`handleLocation`呼び出しを`try`/`catch`し、`CancellationException`は再送出する一方それ以外の例外はログに残して次の位置情報の処理を続けます(1件の評価失敗でコンシューマー全体を道連れにしない)。**停止完了バリア**: `LocationTrackingService`の`companion object`が持つ`consumerJob`(`Job?`、コンシューマーコルーチン自身への参照。`onCreate`で`scope.launch { ... }`の戻り値を代入)と`stopAndAwaitCompletion(context)`は、「新しい位置の受信を止め、キュー済みの評価も含めてコンシューマーコルーチンが完全に終了する」ことを待ち合わせる仕組みです。`stopAndAwaitCompletion`は`Context.stopService`を呼んだ後、保持しておいた`consumerJob`を`Job.join()`で直接待ちます(`consumerJob`が`null`、すなわちサービスが一度も起動していなければ即座に戻ります)。`Context.stopService`の戻り値(サービスが元々動作していたか)は判定に使いません。既に別経路でサービスの停止処理が始まっていると`stopService`が`false`を返す一方、`consumerJob`自体は`handleLocation`の途中でまだ実行中のことがあり、この戻り値で早期リターンすると`evaluateTask()`が`GeofenceStateDao.upsert()`する前に呼び出し元が`deleteAll()`してしまい削除したはずの状態が復活するため、`consumerJob`が非nullなら戻り値に関わらず必ず`join()`します。`Job.join()`は対象のJobが既に終了済み(正常・異常・キャンセルいずれの場合も)であれば即座に戻り、まだ実行中であれば終了まで中断して待つため、`stopAndAwaitCompletion()`が呼ばれるより前に`handleLocation`内の例外でコンシューマーコルーチンが先に異常終了していた場合でも取りこぼさず正しく完了を検知できます(以前は`CompletableDeferred`+`invokeOnCompletion`方式でしたが、`stopAndAwaitCompletion()`呼び出し前にJobが既に終了していると、後から設定した`CompletableDeferred`はそのJobから二度と`invokeOnCompletion`が呼ばれず永久に完了しない不具合がありました)。`stopAndAwaitCompletion`自体も`withContext(NonCancellable)`で包んでおり(`LocationReminderManager.awaitCompletion()`と同じ考え方)、呼び出し元(`LocationReminderManager.switchMode`、ひいては`TaskViewModel.viewModelScope`)が待機中にキャンセルされてもこの停止要求と待ち合わせは中断されません。`LocationReminderManager.switchMode`が連続追跡方式から離れる際は`LocationTrackingService.stopAndAwaitCompletion(context)`の完了後に`geofenceStateDao().deleteAll()`を呼ぶことで、評価中・キュー済みだった書き込みが削除より後に発生して復活してしまう競合を防いでいます(`onDestroy`側は評価がまだ途中でも`job`を`cancel`せず、コンシューマーコルーチンが自然に`for`文を抜けるのに任せることで、キュー済みの最後の要素の処理が完了バリアの前に打ち切られないようにしています)。`switchMode`の本体は`lifecycleMutex.withLock`の内側で丸ごと`withContext(NonCancellable)`にも包んでいます。`stopAndAwaitCompletion()`/`awaitCompletion()`自体は個別にNonCancellableで保護済みですが、それらの完了直後や`setMode()`・`reconcileAllLocked()`の実行中に呼び出し元(`TaskViewModel.viewModelScope`等)がキャンセルされると、旧方式のリソースは解除済みなのに新方式への切り替え(モードの保存・再登録)が完了しないまま処理が中断され、どちらの方式でも位置情報が機能しない不整合な状態が残ってしまうためです。また`LocationTrackingService.onStartCommand`は、位置情報の権限確認に加えて`LocationManagerCompat.isLocationEnabled()`で端末側の位置情報サービス(設定アプリの「位置情報」トグル)が有効かどうかも確認してから`startForeground`を呼びます。権限があっても位置情報サービス自体がオフの場合、Android 14以降は`foregroundServiceType="location"`の`startForeground`が`SecurityException`を投げるため、権限確認だけでは検知できないこのケースを別途弾いています(無効なら`stopSelf()`+`START_NOT_STICKY`)。さらに`startForeground`の直後、`EXTRA_FORCE_RESTART`の処理より前に`LocationTrackingSettings.getMode(this)`を読み直し、`CONTINUOUS_TRACKING`でなければ`stopSelf()`+`START_NOT_STICKY`で停止します。`updateContinuousTrackingInterval`が発行した`restart()`のIntentは配送されるまでに`switchMode()`で確認方式がGeofencing APIへ切り替わり永続化されていることがあり、このモード再確認が無いと、既に選ばれていない連続追跡方式のまま`EXTRA_FORCE_RESTART`を処理して位置情報の購読を開始してしまいます。
