# 位置情報リマインダーの確認方式(連続追跡)

**位置情報リマインダーの確認方式**: 位置情報リマインダーの到着・離脱は**連続追跡方式のみ**で検知します(以前はGoogle Play servicesのGeofencing APIとの切り替え式でしたが、Geofencing APIは内部の評価間隔を端末側で間引くことがあり、実際には数時間前に起きていた遷移がまとめて遅れて通知される「遅延キャッチアップ」が起こるため廃止しました。旧バージョンで登録したジオフェンスの一括解除は`docs/architecture/location-reminders.md`参照)。`notification/LocationTrackingSettings`(SharedPreferences`location_tracking_settings`)が更新間隔(分、`MIN_INTERVAL_MINUTES`=1〜`MAX_INTERVAL_MINUTES`=60、既定`DEFAULT_INTERVAL_MINUTES`=15に丸める)を永続化し、アプリ全体で共通の設定です(タスクごとの個別設定ではありません)。設定画面(`SettingsScreen`)の「位置情報」セクションで更新間隔の入力欄(分、保存ボタンで確定)を提供します。`notification/LocationReminderManager`の`register`は位置情報を使う未完了タスクがあれば`notification/LocationTrackingService`(フォアグラウンドサービス、`android:foregroundServiceType="location"`、`FOREGROUND_SERVICE`・`FOREGROUND_SERVICE_LOCATION`権限が必要)を起動し、`unregister`は該当タスクの基準値を削除したうえで位置情報タスクが残っていなければサービスを停止します(フォアグラウンドサービスの通知は必須。チャンネル`location_tracking_service`は`IMPORTANCE_LOW`〈`IMPORTANCE_MIN`は`startForeground`で使うとシステムが代わりに「バックグラウンドで実行中」のより目立つ通知を出すため使わない〉で、`setOngoing(false)`によりAndroid 14以降はスワイプで消せる〈消してもサービスは継続〉)。`LocationTrackingService`は`FusedLocationProviderClient.requestLocationUpdates`で設定した間隔を希望値として位置の更新を要求し(`LocationRequest.Builder`の`intervalMillis`/`setMinUpdateIntervalMillis`。端末やシステムの状態によっては実際の更新がそれより遅れることがあります)、`taskDao.getPendingWithLocation()`の全件それぞれについて`metersBetween()`で距離を計算し圏内/圏外を判定、前回評価時の状態を`data/GeofenceState`(`taskId`/`isInside`/`latitude`/`longitude`/`radiusMeters`、`AppDatabase`バージョン15→16の`MIGRATION_15_16`で追加した`geofence_states`テーブル。プロセス再起動を挟んでも基準を見失わないようRoomに永続化)と比較して遷移を検知します(初回評価時は、既に圏内かつ到着通知希望の場合のみ即座に扱う)。`latitude`/`longitude`/`radiusMeters`は、記録した`isInside`がどのジオフェンス定義(位置・半径)に基づく評価結果かを表す。`LocationReminderManager.register`はタスクの編集(位置・半径と無関係な項目の変更を含む)のたびに呼ばれるため、記録済みの定義がタスクの現在の設定と一致する場合は基準値をそのまま保持し(無駄な初回評価扱いによる到着通知の再送を避ける)、位置・半径が実際に変わった場合のみ削除して次回評価を初回評価扱いにする。`LocationTrackingService.evaluateTask`側でも同様の一致確認を行い、万一削除し損ねた基準値が残っていても誤判定しないようにしている。遷移を検知した後は`GeofenceConfirmWorker.schedule()`(3分デバウンス)へ回し、位置情報の更新履歴(`docs/architecture/location-update-log.md`参照)にも`〈連続追跡〉`のdetail付きで記録します。`updateContinuousTrackingInterval(context, minutes)`は間隔変更時、位置情報タスクがあればサービスを再起動して即座に新間隔を反映します。`BootReceiver`は`LocationReminderManager.register`経由で端末再起動後にサービスを再開します。**排他制御**: `register`/`unregister`/`reconcileAll`/`updateContinuousTrackingInterval`はいずれも`LocationReminderManager`が持つ単一の`Mutex`で直列化しています。これらは複数の独立したコルーチン(`TaskViewModel`の各操作・`BootReceiver`・設定画面からの更新頻度変更)から並行に呼ばれうるため、直列化しないと例えば最後の位置情報タスクの解除でサービスを停止した直後に古い`updateContinuousTrackingInterval`呼び出しが完了してサービスを再起動してしまう、といった順序崩れが起こりえます。内部的には各公開関数がロックを取得したうえで`registerLocked`等の非公開実装に委譲し、`reconcileAll`から`register`を呼ぶ場合のように関数間で連鎖する処理は非公開実装同士を直接呼び合うことで同じロックの二重取得(デッドロック)を避けています。また`LocationTrackingService`は`onLocationResult`から直接評価用コルーチンを起動するのではなく、`Channel<Location>`(`CONFLATED`。評価〈Room読み書き・ワーカー予約・ログ書き込みを含む〉が設定間隔より時間がかかってコンシューマーが遅れても、未処理の位置情報が無制限に溜まり続けないよう、最新の1件のみ保持し古いものは破棄する)に`trySend()`で積むだけに留め、`onCreate`で1つだけ起動する単一のコンシューマーコルーチンが順に`for (location in locationChannel)`で取り出して評価します(`scope.launch`を毎回呼ぶ方式だと、コルーチンの起動自体は非同期なため開始順序がコールバックの到着順と入れ替わりうるが、`trySend`は同期的にキューへ積むだけなので到着順がそのまま処理順になる)。このコンシューマーは`SupervisorJob`配下で動作しますが、`handleLocation`(Room操作・`GeofenceConfirmWorker.schedule`等を含む)が`CancellationException`以外の例外を投げた場合にループ自体を抜けて終了してしまうと、`SupervisorJob`のおかげで親の`scope`は無事でもこのコンシューマー自身は二度と再開せず、以後受信する位置情報が一切評価されなくなってしまいます。これを避けるため、`for`ループ内で`handleLocation`呼び出しを`try`/`catch`し、`CancellationException`は再送出する一方それ以外の例外はログに残して次の位置情報の処理を続けます(1件の評価失敗でコンシューマー全体を道連れにしない)。また`LocationTrackingService.onStartCommand`は、位置情報の権限確認に加えて`LocationManagerCompat.isLocationEnabled()`で端末側の位置情報サービス(設定アプリの「位置情報」トグル)が有効かどうかも確認してから`startForeground`を呼びます。権限があっても位置情報サービス自体がオフの場合、Android 14以降は`foregroundServiceType="location"`の`startForeground`が`SecurityException`を投げるため、権限確認だけでは検知できないこのケースを別途弾いています(無効なら`stopSelf()`+`START_NOT_STICKY`)。
