# アーキテクチャ詳細

各機能の実装詳細。CLAUDE.md からは概要のみを参照し、機能ごとの詳細はここに集約する。

## 基本情報

パッケージ名/applicationId: `com.toshi0907.oboetotte`、minSdk 26、target/compileSdk 35。

## Kotlin/AGP/Composeコンパイラプラグイン

Kotlin 2.0.21 + AGP 8.7.3。**Composeを使うには別途`org.jetbrains.kotlin.plugin.compose`というGradleプラグインが必須**です(ルートの`build.gradle.kts`と`app/build.gradle.kts`の両方に適用済み)。Kotlin 2.0以降、従来の`composeOptions.kotlinCompilerExtensionVersion`による指定方法は機能せず、指定しないと「Compose Compiler Gradle plugin is required」というエラーでビルドが失敗します。Kotlinのバージョンを上げる際は、この2箇所のプラグイン指定を同期させてください。

## 永続化層(Room)

永続化層は`app/src/main/java/com/toshi0907/oboetotte/data/`に置いています(`Task`/`TaskList`/`SavedLocation`/`TaskAttachment`エンティティ、`TaskDao`/`TaskListDao`/`SavedLocationDao`/`TaskAttachmentDao`、`AppDatabase`)。`Task`は`id`/`title`/`isDone`/`dueAt`(epoch millis、任意)/`listId`(`TaskList`への外部キー、任意)/`parentTaskId`(サブタスク用の自己参照、任意)/`repeatRule`(繰り返しルール、任意)/`repeatDaysOfWeek`(`repeatRule`が`WEEKLY_DAYS`の場合のみ使う、選択曜日のカンマ区切り文字列、任意)/`locationName`・`latitude`・`longitude`・`radiusMeters`・`notifyOnArrival`・`notifyOnDeparture`(位置情報リマインダー用、任意。詳細は後述)/`url`・`memo`(任意。`url`は通知に「リンクを開く」ボタンとして表示、`memo`は`EditTaskDialog`を開くと表示・編集できる自由記述の文字列。詳細は後述)/`seriesId`(繰り返しタスクが完了して次回分が生成される際に引き継がれる、同じ繰り返しシリーズを束ねるID。任意、詳細は後述の「タスクへのファイル添付」参照)/`aiPrompt`・`aiCachedResponse`・`aiUseWebSearch`・`aiUseMaps`・`aiUseUrlContext`・`aiCachedSources`(AI連携〈Gemini〉用、任意。詳細は後述)/`autoSnoozeMinutes`(オートスヌーズの間隔・分、任意。詳細は後述の「リマインダー通知」参照)/`notifyOnlyMode`(通知のみタスク、既定`false`。詳細は後述の「リマインダー通知」参照)を持ちます。いずれもRoom上の`@ForeignKey`制約は付けていません。サブタスクも`Task`と同じテーブル・同じエンティティで表現しており、`parentTaskId`の有無でトップレベルタスクかサブタスクかを区別します。`TaskDao.getAll`は`ORDER BY isDone ASC, dueAt IS NULL ASC, dueAt ASC, id DESC`で全件(トップレベル+サブタスク)を取得し、未完了→期限が近い順→期限なしの順に並びます。`AppDatabase.getInstance(context)`でシングルトンのRoomデータベース(`oboetotte.db`)を取得する構成です。

## TaskViewModel

`TaskViewModel`(`AndroidViewModel`)が両DAOをラップし、`allTasks: StateFlow<List<Task>>`(全件、サブタスク含む)、`tasks: StateFlow<List<Task>>`(`allTasks`を`parentTaskId == null`・選択中の`selectedListId`・`showCompleted`〈デフォルト`false`。`false`なら完了済みのトップレベルタスクを除外〉でフィルタした一覧表示用。この完了済みフィルタはトップレベルタスクにのみ適用され、表示中の親の配下のサブタスクは`TaskTreeRow`/`SubtaskTreeRow`側でこれまでどおり全件表示されます)、`lists: StateFlow<List<TaskList>>`を公開しています。操作系は、タスクの追加(`addTask`、選択中のリストに紐づく。期限〈`dueAt`〉は登録時刻の`DEFAULT_DUE_DELAY_MILLIS`〈1時間〉後をデフォルトで設定し、`ReminderScheduler.schedule`も同時に呼び出す)・完了切り替え(`toggleDone`、サブタスクにも共用。完了にする側の実処理は`TaskCompletion.complete`に委譲し、未完了に戻す側のみ`taskDao.setDone`+`ReminderScheduler.schedule`+`LocationReminderManager.register`をここで直接行う)・タイトル/所属リスト/期限/繰り返しルール/位置情報の更新(`updateTask(task, edits: TaskEdits)`。`TaskEdits`〈`TaskViewModel.kt`内〉は`EditTaskDialog`で編集可能な全項目をまとめたdata classで、編集ダイアログの項目が増えるたびに`updateTask`の引数を増やす代わりにここへフィールドを追加する)・削除(`deleteTask`)・サブタスク追加(`addSubtask(parent, title)`。`addTask`と同様に期限のデフォルト値〈1時間後〉を設定し`ReminderScheduler.schedule`を呼ぶ)、リストの追加/改名/削除(`addList`/`renameList`/`deleteList`。削除時は`TaskDao.clearListId`でそのリストに属するタスクの`listId`をNULLに戻してから削除)、完了済みタスクの表示切り替え(`setShowCompleted`)。`TaskDao.update`は`@Update`によるRoom標準の全カラム更新です。`savedLocations: StateFlow<List<SavedLocation>>`(名称の昇順)も公開しており、`addSavedLocation(name, latitude, longitude, radiusMeters)`/`updateSavedLocation(location, name, radiusMeters)`〈名称・半径のみ変更可、座標はそのまま〉/`deleteSavedLocation(location)`で操作します(詳細は後述)。

## 繰り返しタスク

**繰り返しタスク**: `repeatRule`は`RepeatRule`(`TaskViewModel.kt`内の`object`)で定義した`"DAILY"`/`"WEEKLY"`/`"WEEKLY_DAYS"`/`"MONTHLY"`のいずれかです。カスタム間隔(2日おき等)は未対応です。`WEEKLY_DAYS`(UI表示「毎週(曜日)」)は、`Task.repeatDaysOfWeek`にISO-8601の曜日番号(月曜=1〜日曜=7)をカンマ区切りで保存し(`RepeatRule.parseDaysOfWeek`/`formatDaysOfWeek`で相互変換)、複数曜日を選択できます。`EditTaskDialog`で「毎週(曜日)」を選択すると月〜日の`Checkbox`が7つ表示され、最低1つ選択しないと(`selectedDays.isEmpty()`)保存ボタンが無効化されます。タスクを完了にする処理は`TaskCompletion.complete(context, task)`(`TaskCompletion.kt`、アプリ内・通知の両方から共通利用)に集約しており、`repeatRule`と`dueAt`が両方設定されていれば(`WEEKLY_DAYS`の場合はさらに`repeatDaysOfWeek`が空でなければ)`nextDueAt()`(同ファイル内のプライベート関数、`java.time`でローカルタイムゾーンの日時を加算)で次回の期限を計算し、同じタイトル/リスト/親/繰り返しルール/曜日設定を持つ未完了の新規タスクを`taskDao.insert`で生成します。`WEEKLY_DAYS`の次回期限は、現在の期限日の翌日から最大7日分を順に調べ、選択された曜日のうち最も近い日(同じ週内も含む)を採用します。`dueAt`が未設定の繰り返しタスクは、完了しても次回分は生成されません。次回分の生成時は`nextTask.seriesId = task.attachmentGroupId()`(`Task.attachmentGroupId()`、`Task.kt`内の拡張関数で`seriesId ?: id`)を設定して引き継ぎます。これにより繰り返しシリーズの全インスタンス(初回・完了済みの過去分・現在未完了の分すべて)が同じ`seriesId`(初回インスタンスのみ`seriesId`が`null`のままなので、その場合は自分自身の`id`)を共有し、添付ファイルの紐付け(後述の「タスクへのファイル添付」参照)が繰り返しのたびに途切れず連動し続けます。

## 画面構成(MainActivity)

**画面構成**: `MainActivity`はNavigation Compose等のライブラリを使わず、`setContent`内の`var currentScreen by remember { mutableStateOf(MainScreen.Tasks) }`(`MainScreen`は`MainActivity.kt`内のプライベートな`enum class`で`Tasks`/`Settings`の2値)を`when`で分岐させ、`TaskScreen`と`SettingsScreen`のどちらかをメイン画面全体として描画するだけのシンプルな構成です(両画面とも`Scaffold`の同じ`innerPadding`を共有)。`TaskScreen`側は末尾の「設定」`AssistChip`の`onOpenSettings`で`currentScreen = MainScreen.Settings`に、`SettingsScreen`側は先頭の「← 戻る」`TextButton`の`onBack`で`currentScreen = MainScreen.Tasks`に戻します。`SettingsScreen`は`BackHandler`(`androidx.activity.compose`)でシステムの「戻る」操作(戻るジェスチャー・戻るボタン)も同じ`onBack`にフックしており、アプリ終了ではなくタスク一覧への復帰として扱われます。

## タスク一覧画面(TaskScreen)

`MainActivity.kt`の`TaskScreen`が一覧UIです(表示は`tasks`、ツリー描画や確認・編集ダイアログへの受け渡しには`allTasks`を使います)。上部は「リスト」ラベル付きの`FilterChip`行(すべて/リスト未登録〈`listId == null`のタスクのみ表示。フィルタ専用の値で`TaskViewModel.UNASSIGNED_LIST_ID`〈`-1L`。Roomの`TaskList.id`は`autoGenerate`で1から始まるため実在のリストIDと衝突しない〉を`selectedListId`にセットして表す〉+各リスト)でリストを切り替える行と、その下のもう1つの行(「完了済みを表示」`FilterChip`〈選択状態=`showCompleted`〉、「設定」`AssistChip`)の2段に分かれており、リスト選択とそれ以外の操作が視覚的に区別されています。**タスク行タップ時の挙動**: 一覧の行をタップすると、まず読み取り専用の確認ダイアログ`TaskDetailDialog`が開きます(直接`EditTaskDialog`は開きません)。`TaskDetailDialog`は`EditTaskDialog`と同じ項目(タイトル・所属リスト・URL・期限・繰り返しルール・位置情報・メモ・添付ファイル・サブタスク一覧)をすべて表示しますが、上部の「編集」ボタンを押すまでは値を書き換える操作(添付ファイルの追加・削除、サブタスクの追加を含む)は行えません。チェックボックスによる完了/未完了の切り替えと、添付ファイルをタップして外部アプリで開く操作だけは確認ダイアログ上でも直接行えます。「編集」ボタンを押すと、その場に(確認ダイアログの上に重ねて)`EditTaskDialog`が開き、タイトル・所属リスト(`FilterChip`で「なし」+各リストから選択。メイン画面の「リスト」フィルタとは独立で、ここでの選択がそのままタスクの`listId`を書き換えます)・期限・繰り返しルール(`FilterChip`で「なし/毎日/毎週/毎月」を選択)に加えてサブタスクの一覧(チェック可能)と追加フォームを編集できます。`EditTaskDialog`自体の内容・保存挙動は本機能追加前から変更していません。

## 設定画面(SettingsScreen)

**設定画面(`SettingsScreen`)**: 「設定」`AssistChip`から遷移する全画面です。以前メイン画面のチップに散らばっていた補助的な操作(リストを編集・場所を編集・テスト通知・位置情報デバッグ)と、既存のバックアップ(エクスポート/インポート)をここに集約しています。セクションは上から「アップデート」(アプリ内アップデート、詳細は後述)・「リスト」(「リストを編集」から`ManageListsDialog`。リストの追加・改名・削除)・「場所」(「場所を編集」から`ManageLocationsDialog`。保存済みの場所の管理)・「位置情報」(位置情報リマインダーの確認方式、詳細は後述)・「バックアップ」(従来`SettingsDialog`だった内容。説明文+「エクスポート」「インポート」ボタンをそのままインライン表示)・「クラウド自動バックアップ」(詳細は後述)・「AI連携」(詳細は後述)・「デバッグ」(「テスト通知」ボタン・「位置情報デバッグ」ボタン〈`LocationDebugDialog`を開く〉・「通知履歴」ボタン〈`NotificationLogDialog`を開く。詳細は後述〉・「AIテスト実行」ボタン)、の順に並びます。ボタンをタップして開く`ManageListsDialog`/`ManageLocationsDialog`/`LocationDebugDialog`/`NotificationLogDialog`自体は従来どおりダイアログのままで、`SettingsScreen`という1枚の全画面から呼び出す形になっています。新機能を追加する際、それがメイン画面での日常的な操作ではなく設定・管理・デバッグの類であれば、メイン画面のチップを増やすのではなくこの`SettingsScreen`にセクションを追加してください。**新しいセクション・項目をこの画面に追加する際は、挿入位置(どのセクションの前後に置くか)をユーザーに確認してから追加してください。上記の並び順を含め、セクションの並び順はユーザーの日常的な利用頻度・優先度を反映した意図的なものであり、Claude Codeの判断だけで並び順を変更・追加しないこと。**「アップデート」セクションには、現在のビルド(`BuildConfig.GIT_COMMIT_SHA`)・直近の更新チェック時刻(`updateLastCheckedAt`。`update/AppUpdateCheckSettings`にSharedPreferencesで永続化し、アプリ起動時の自動チェック・この画面の「更新を確認」ボタン・バックグラウンドの定期チェック〈`AppUpdateCheckWorker`〉のいずれで更新した時刻も反映)・チェック結果に応じた文言・「更新を確認」ボタンを表示します。「ダウンロードしてインストール」ボタン(`TaskScreen`側のバナーにある「更新する」ボタンも同様)は、APKのダウンロードにインストールダイアログが表示されるまで時間がかかりタップできたかどうか分かりづらいことがあったため、ダウンロード中は`isDownloadingUpdate`により無効化しつつラベルを「ダウンロード中…」に変えて処理中であることを示します。

## サブタスクのツリー表示

**メイン画面・確認ダイアログ双方でのサブタスクのツリー表示**: メイン画面のタスク一覧(`TaskScreen`内の`LazyColumn`)は、トップレベルタスク(`tasks`)それぞれを起点に`TaskTreeRow`(再帰的なComposable)で描画しており、直接の子だけでなく孫・ひ孫…まで`depth * 20.dp`のインデント付きで一覧に表示されます。各行のタップで`TaskDetailDialog`(確認ダイアログ、前項)を開き、長押しで削除確認ダイアログを開きます(`combinedClickable`はFoundationのExperimental API)。`TaskDetailDialog`内のサブタスク一覧は同様の考え方の`SubtaskTreeRow`(チェックボックスとタイトルのみの簡易版、行タップで`onOpenTask`コールバック経由の`nestedViewTask`状態を介して、そのサブタスク自身の`TaskDetailDialog`が重ねて開く。`EditTaskDialog`内のサブタスク一覧も同じ`SubtaskTreeRow`を使っていますが、こちらは`nestedTask`状態を介して`EditTaskDialog`自身が重ねて開きます)で描画しています。`TaskTreeRow`・`TaskDetailDialog`・`EditTaskDialog`のいずれも`allTasks`をそのままツリー描画・再帰呼び出しに渡し、各ノードは`allTasks.filter { it.parentTaskId == node.id }`で自分の子だけを算出するため、サブタスクの階層数に上限はありません。**期限の色分け**: `TaskTreeRow`は期限行(`formatDueAt`等の文字列)の文字色を、未完了かつ期限切れ(`isOverdue`)なら`MaterialTheme.colorScheme.error`、未完了かつ期限が当日(`isDueToday`。`task.dueAt`と`nowMillis`をそれぞれ`Instant.atZone(ZoneId.systemDefault()).toLocalDate()`で比較)なら緑系(`ui/theme/Color.kt`の`Green80`/`Green40`。ダイナミックカラー〈`dynamicColor = true`時、端末の壁紙に応じて`tertiary`等のテーマ色が変わる〉の影響を受けないよう固定値にしており、`isSystemInDarkTheme()`でダーク/ライトどちらのテーマかに応じて明るい`Green80`/暗い`Green40`を切り替える)、それ以外は`onSurfaceVariant`に出し分けます。`nowMillis`は`TaskScreen`側で`produceState`(1分おきに`delay`+更新を繰り返す無限ループ)により保持し`TaskTreeRow`へ(再帰呼び出しも含め)引数で渡しています。`System.currentTimeMillis()`や`LocalDate.now()`をComposable内で直接呼ぶと値の変化そのものは再コンポーズをトリガーしないため、タスク一覧を開いたまま日付をまたいでも色分けが更新されない問題があり、この`nowMillis`をstateとして持たせることで解消しています。`SubtaskTreeRow`は期限を表示しないため対象外です。

## 期限ピッカー・DBマイグレーション

期限は`DatePickerDialog`+`TimePicker`(いずれも`@ExperimentalMaterial3Api`)を連続で開いて設定・クリアでき、`DatePicker`が返す`selectedDateMillis`はUTC 0時のepoch millisなので、選択した時刻と合成する際は`combineDateAndTime()`(`MainActivity.kt`内のプライベート関数)でローカルタイムゾーンに変換しています。`EditTaskDialog`の「設定」ボタンをタップして期限ピッカーを開いた時点でまだ期限(`dueAt`)が未設定の場合、`DatePicker`の初期選択日は`todayAsDatePickerMillis()`(端末のローカルタイムゾーンでの「今日」をUTC 0時基準のepoch millisに変換するプライベート関数)、`TimePicker`の初期時刻は`LocalTime.now()`となり、いずれも現在日時がデフォルト表示されます(既に`dueAt`が設定済みの場合は、その日時をそのまま初期値として表示します)。この挙動はタスク追加時のデフォルト値(`TaskViewModel.addTask`/`addSubtask`が設定する登録時刻の1時間後、前述)とは無関係です。**期限のクイック選択**: 「設定」/「クリア」ボタンの下に`DUE_QUICK_OPTIONS`(`MainActivity.kt`内、ラベルと「タップ時点の現在時刻(epoch millis)→期限(epoch millis)」を計算する関数`(Long) -> Long`のペアのリスト。5分後/15分後/30分後/1時間後/3時間後/6時間後/1日後/1週間後/1ヶ月後)ぶんの`AssistChip`を並べており、タップすると`dueAt`に計算結果を直接セットします(カレンダー/時刻ピッカーを介さない簡易入力)。日・週は固定長のため`addMinutes()`で分加算するだけですが、月は日数が28〜31日と変動するため`addMonths()`で`java.time`の`plusMonths(1)`によるカレンダー月単位の加算を行います(`TaskCompletion.nextDueAt`の繰り返しタスクの月加算と同じ考え方)。他の項目と同様にダイアログ内の状態を書き換えるだけで、「保存」ボタンを押すまでDBには反映されません。**DBマイグレーション**: `AppDatabase`はバージョン6以降、明示的な`Migration`オブジェクト(`MIGRATION_6_7`〜`MIGRATION_10_11`、`AppDatabase.kt`内の`companion object`に定義)で`ALTER TABLE`/`CREATE TABLE`のSQLを直接実行し、アプリ更新時に端末内のデータを保持したままスキーマを更新します(以前は`fallbackToDestructiveMigration()`のみでデータが破棄されていましたが、実運用でのデータ消失が問題になったため導入しました)。**エンティティのスキーマを変更する際は、`@Database`の`version`を上げるのに加えて、必ず新しいバージョンへの`Migration`を追加し`addMigrations()`に登録してください。** 追加を怠ると、そのバージョン間で更新したユーザーのデータが失われます。`fallbackToDestructiveMigration()`は、対応する`Migration`が定義されていない古いバージョン(6より前)からの更新時のみ働く最終手段として残しています。

## リマインダー通知

**リマインダー通知**: `app/src/main/java/com/toshi0907/oboetotte/notification/`に`ReminderScheduler`(スケジュール/キャンセル)・`ReminderReceiver`(`BroadcastReceiver`、通知表示)・`BootReceiver`(端末再起動後の再スケジュール)を置いています。`ReminderScheduler.schedule(context, task)`は、`dueAt`が未来かつ`isDone == false`の場合に`AlarmManager.setExactAndAllowWhileIdle`でタスクIDを`PendingIntent`のリクエストコードとしたアラームを登録し、条件を満たさなければ`cancel`を呼びます。API 31(S)以降は`AlarmManager.canScheduleExactAlarms()`で正確なアラームの権限有無を確認し、無ければスケジュールをスキップします(`MainActivity`のバナーから`Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM`で設定画面へ誘導)。`TaskViewModel`の`updateTask`・`toggleDone`(繰り返しタスクの次回生成分を含む)・`deleteTask`からこの`schedule`/`cancel`を呼び出し、常にDBの状態とアラームの登録状態を同期させています。`ReminderReceiver`は発火時にRoomから最新のタスク情報を`taskDao.getById`で取得し直し(タイトル変更や削除に追従)、未完了であれば通知チャンネル`task_reminders`で通知を表示します。`BootReceiver`は`RECEIVE_BOOT_COMPLETED`を受けて`taskDao.getPendingWithDueDate()`の全件を再スケジュールします。API 33(TIRAMISU)以降は`POST_NOTIFICATIONS`権限が必要なため、`MainActivity.onCreate`で未許可なら都度リクエストしています。設定画面(`SettingsScreen`)の「テスト通知」ボタンからは`ReminderScheduler.scheduleTestNotification(context)`を呼び出し、タスクに紐づかない実際のアラーム経路(`TEST_DELAY_SECONDS`=5秒後、`ReminderReceiver`が`EXTRA_IS_TEST`フラグを見てDB参照無しで固定文言の通知を表示)を使って通知が届くかどうかを、本番と同じ経路のまま検証できます。**スヌーズ**: Androidの通知は表示できるアクションボタンが実質最大3個程度に制限されており(それ以上`addAction`しても通知欄には表示されないだけで、明示的なエラーにはならない)、以前は`ReminderScheduler.SNOOZE_OPTIONS`(15分後/30分後/1時間後/3時間後/1日後)の5件をボタンとして直接並べていたため、「完了」やURLの「リンクを開く」ボタンと合わせた際に一部のボタンが表示されない不具合があった。これを解消するため、タスクの通知(テスト通知は対象外)には「スヌーズ」ボタンを1つだけ付与しており、タップすると`notification/SnoozePickerActivity`(`Theme.Oboetotte.SnoozeDialog`でウィンドウ自体を透過にし、Compose側の`AlertDialog`だけを表示する専用Activity)が起動します。ダイアログで`SNOOZE_OPTIONS`のいずれかを選んだ時点で現在の通知(`NOTIFICATION_TAG_DUE`)を消去し、`ReminderScheduler.scheduleSnooze(context, taskId, minutes)`で「タップ時刻+選択した分数」後に再度アラームを発火させて`finish()`します(何も選ばず「キャンセル」や外側タップで閉じた場合は通知に触れないため、元のリマインダー通知がそのまま残ります)。**タスクの`dueAt`自体は変更しません**(スヌーズは通知タイミングだけをずらすもので、期限の再設定ではないため)。`scheduleSnooze`はアラーム本体(`schedule`/`cancel`)と同じ`pendingIntentFor`(リクエストコード=`taskId.toInt()`、`ReminderReceiver`宛)を再利用して発火時刻だけを書き換えているので、後から`updateTask`等で`schedule`/`cancel`が呼ばれれば通常どおり上書き・キャンセルされます。「スヌーズ」ボタン自身の`PendingIntent`(`snoozePickerPendingIntent`、`SnoozePickerActivity`宛)は`taskId.toInt() * 10 + 5`をリクエストコードとして使います。**オートスヌーズ**: `Task.autoSnoozeMinutes`(任意、`SNOOZE_OPTIONS`と同じ分数のいずれか)をタスクごとに設定しておくと、`ReminderReceiver`が期限日時通知(通常発火・手動スヌーズ・オートスヌーズいずれの経路でも)を表示した直後、そのタスクが未完了であれば`ReminderScheduler.scheduleAutoSnooze(context, taskId, minutes)`で「表示時刻+`autoSnoozeMinutes`分後」に次のアラームを予約し、完了するまで上限なく再通知を繰り返します。このアラームは`pendingIntentFor`が組み立てる同じ`PendingIntent`(taskIdをリクエストコードとする枠、`EXTRA_IS_AUTO_SNOOZE`で識別)を`schedule`/`scheduleSnooze`と共有しているため、手動で「スヌーズ」を選ぶとその時刻を基準に次回のオートスヌーズが計算し直され(手動スヌーズが優先)、`dueAt`の変更やタスク完了による`schedule`/`cancel`が呼ばれれば通常どおり上書き・キャンセルされます。`schedule`は`dueAt`が過去(期限到達後)の場合、通常は通知済みとみなしキャンセルするだけですが、`autoSnoozeMinutes`が設定された未完了タスクに限りキャンセルせず「今から指定間隔後」を基準にオートスヌーズを立て直します(端末再起動時の`BootReceiver`の再スケジュールや、期限日時を変えずに他の項目だけを編集した`updateTask`経由の呼び出しのたびに、進行中のオートスヌーズが理由なく止まってしまうことを避けるため)。通知履歴(`NotificationLog`)の`triggerCondition`には手動スヌーズ経由と区別して「オートスヌーズ経由の再通知」と記録され、AI要約(前述)はオートスヌーズ経由でも手動スヌーズと同様に`aiCachedResponse`を再利用しAPIは再呼び出ししません。`EditTaskDialog`の「繰り返し」直下、`TaskDetailDialog`にそれぞれ設定・表示できます。**通知のみタスク**: `Task.notifyOnlyMode`(タスクごとに個別設定、既定`false`)を有効にすると、通知されること自体が重要でタスク完了の確認が不要なタスク向けに、期限日時通知(位置情報通知は対象外)を実際に表示できた時点で`ReminderReceiver`が`TaskCompletion.complete(context, task)`を呼び自動的に完了にします(繰り返しタスクならそのまま次回分が生成・スケジュールされる)。`NotificationManagerCompat.notify`が権限不足等で呼べず通知を実際には表示できなかった場合は完了させません(通知されないままタスクが消えてしまうことを避けるため、`showNotification`の戻り値`posted`を見てから完了処理を行う)。この機能は「スヌーズ機能は使わない」仕様のため、通知には「完了」「スヌーズ」ボタンをいずれも付与せず(`showTaskActions = false`相当)、`autoSnoozeMinutes`とは併用しません。`TaskViewModel.updateTask`は`edits.notifyOnlyMode`が`true`の場合に`autoSnoozeMinutes`を強制的に`null`へ正規化し(`EditTaskDialog`側もこの条件下ではオートスヌーズの選択UI自体を表示しません)、両者が同時に有効な状態にならないようにしています。通知履歴の`triggerCondition`には「(通知のみ・自動完了)」が付記されます。`EditTaskDialog`の「繰り返し」直下、`TaskDetailDialog`にそれぞれ設定・表示できます。この自動完了経路の追加により、同じタスクに対して`ReminderReceiver`(自動完了)とアプリ内のチェックボックス/通知の「完了」ボタン(手動完了)がほぼ同時に`TaskCompletion.complete`を呼ぶ競合が従来より起きやすくなったため、`TaskDao.setDone(taskId, isDone)`は`WHERE id = :taskId AND isDone != :isDone`という条件で実際に状態遷移した行数(`Int`)を返すようにしており、`TaskCompletion.complete`はこれが`0`件(=既に他方の呼び出しが完了させていた)であれば繰り返しタスクの次回分生成を行わずに早期returnします(渡された`task`スナップショットの`isDone`は呼び出し時点で古い可能性があるため、判定はDBへの書き込み結果そのものを見て行う)。**完了ボタン**: タスクの通知には「完了」ボタンも付与しており、タップすると`notification/CompleteReceiver`が起動して現在の通知を消し、対象タスクが未完了のまま残っていることを確認した上で`TaskCompletion.complete(context, task)`(アプリ内のチェックボックスから完了にする場合と同じ共通処理。繰り返しタスクなら次回分の生成・スケジュールも行う)を呼びます。`completePendingIntent`は`CompleteReceiver`宛・リクエストコード`taskId.toInt()`です。**通知タグ**: `ReminderReceiver`(期限日時)は`ReminderScheduler.NOTIFICATION_TAG_DUE`、`GeofenceReceiver`(位置情報、後述)は`NOTIFICATION_TAG_LOCATION`という別々のタグを付けて`NotificationManagerCompat.notify(tag, id, ...)`しています(通知ID自体は「完了」ボタンの消去用途のため両方`taskId.toInt()`で揃えていますが、`notify`の実体は`(タグ, ID)`の組で識別されるため、同じタスクに期限日時・位置情報の両方のリマインダーを設定していて両方が発火した場合でも、タグが異なることで片方がもう片方を通知欄から消してしまうことなく両方とも表示されます)。`CompleteReceiver`は両方のタグを`cancel`してタスク完了時にどちらの通知も消し、`SnoozePickerActivity`(スヌーズボタンは期限日時通知にのみ付く)はスヌーズ時間の選択確定時に`NOTIFICATION_TAG_DUE`のみを`cancel`します。

## AI連携(Gemini)

**AI連携(タスク通知へのGemini要約)**: `app/src/main/java/com/toshi0907/oboetotte/ai/`に`GeminiSettings`(APIキー・使用モデルをSharedPreferences`gemini_settings`で永続化)・`GeminiClient`(Gemini APIの`generateContent`呼び出し)を置いています。リポジトリはpublicなためAPIキーはコード・ビルド設定に一切含めず、ユーザー自身が発行したキーを設定画面(`SettingsScreen`)の「AI連携」セクションで入力し端末内にのみ保存する運用です。同セクションではモデル(`GeminiModel`列挙、`gemini-2.5-flash`/`gemini-2.5-flash-lite`〈既定〉/`gemini-3.5-flash-lite`の無料枠があるFlash系のみを候補にした`FilterChip`選択)も選べます。Geminiのモデルは数ヶ月単位で廃止される入れ替わりが速く(例: `gemini-2.0-flash`は2026年6月1日付で廃止済みのため候補から削除し、`GeminiModel.fromName`で保存済みのその値を`DEFAULT`へ読み替える互換処理を残しています)、候補・既定値は今後も見直しが必要です。`GeminiClient`は`AppUpdateChecker`と同じ方針で追加ライブラリ(Google AI SDK)を使わず`HttpURLConnection`+`org.json`の素のHTTP POSTで実装しています。`EditTaskDialog`の「メモ」直下に任意項目「AIプロンプト」(`Task.aiPrompt`)があり、設定したタスクは期限日時の通知(`ReminderReceiver`)が発火するタイミングでのみ(位置情報通知は対象外)、`aiPrompt`とAPIキーの両方が設定されていればGeminiへ問い合わせ、結果を`NotificationCompat.BigTextStyle`で通知本文に追記します。`ReminderReceiver`は`BroadcastReceiver`のためネットワークI/Oを直接実行できず、既存の`goAsync()`+`Dispatchers.IO`の経路(前述)上でそのまま呼び出しており、goAsyncの実行時間制限内に収まるよう`GeminiClient.NOTIFICATION_TIMEOUT_MILLIS`(接続・読み込み各4秒、合計最大8秒程度)を設定しています。タイムアウト・APIエラー時も通知自体は必ず表示し、本文に「AI要約: 取得に失敗しました」と明記してフォールバックします(通知が握りつぶされてユーザーが気づけない状態を避けるため)。**キャッシュ**: 通常の期限到達時のみ新規にGeminiを呼び出し、結果を`Task.aiCachedResponse`(`TaskDao.updateAiCachedResponse`)へ保存します。`ReminderScheduler.scheduleSnooze`経由のスヌーズ再通知では常にこの`aiCachedResponse`を再利用し(初回呼び出しが失敗してキャッシュが無い場合を含め)、APIを再度呼び出しません(同じプロンプトに対して通知のたびにAPIを呼び直さないため)。初回呼び出しが失敗した場合、スヌーズ後の通知はAI要約なしの通常の通知になります(失敗した旨は初回の通知で既に示しているため)。`TaskViewModel.updateTask`は`TaskEdits.aiPrompt`/`aiUseWebSearch`/`aiUseUrlContext`のいずれかが変更された場合に`aiCachedResponse`/`aiCachedSources`を`null`にクリアします(プロンプトや使用ツールを変えたのに古い結果を使い回さないため)。通知履歴(`NotificationLog`)の`triggerCondition`にはAI呼び出しの成否を`(AI要約: 成功)`/`(AI要約: 失敗)`として付記します。設定画面のデバッグセクションには「AIテスト実行」ボタン(`GeminiTestDialog`)があり、通知の発火を待たずに`TaskViewModel.testGeminiPrompt`で任意のプロンプトを試せます(タイムアウトは`GeminiClient.TEST_TIMEOUT_MILLIS`=15秒と、通知経由より長めに設定)。`TaskDetailDialog`(確認画面)では`aiPrompt`と直近の`aiCachedResponse`を読み取り専用で表示します。バックアップのJSON形式にも`aiPrompt`/`aiCachedResponse`が他の任意フィールドと同様に含まれます(旧形式のファイルにはキー自体が無いため`JSONObject.isNull`により後方互換を保っています)。**組み込みツール(Web検索・URLコンテキスト)**: `Task.aiUseWebSearch`/`Task.aiUseUrlContext`(いずれもBoolean、既定`false`)で、Gemini APIの組み込みツール`google_search`(Web検索によるグラウンディング)・`url_context`(プロンプト中のURLの内容を取得してコンテキストに使う)をタスクごとに個別に有効化できます。`EditTaskDialog`の「AIプロンプト」直下・設定画面の「AIテスト実行」(`GeminiTestDialog`)双方で共通の`AiToolCheckboxes`(2つの`Checkbox`)から選択します。`GeminiClient.generateContent`は有効なツールぶんだけ`tools`配列(各要素は`{"google_search": {}}`のように、protoのフィールド名(スネークケース。generativelanguageのv1beta `Tool`メッセージの`google_search`/`url_context`フィールドに対応し、protobufのJSONパーサはこのスネークケース表記もcamelCase表記も受理するため、あえてproto定義そのままの表記にしている)をキーに持つ空オブジェクト)を`generateContent`のリクエストボディに追加します。レスポンス側は`candidates[0].groundingMetadata.groundingChunks`(`google_search`。各チャンクの`web`オブジェクトから`uri`/`title`を取る)と`candidates[0].urlContextMetadata.urlMetadata`(`url_context`。`urlRetrievalStatus`が`URL_RETRIEVAL_STATUS_SUCCESS`のエントリのみ対象とし、`retrievedUrl`を取る。取得失敗〈`ERROR`/`UNSAFE`等〉でも`retrievedUrl`自体は返るため、ステータスを見ずに使うと実際にはコンテキストとして使われなかったURLを出典として表示してしまう)から出典を集め、`GeminiClient.Source(title, uri, origin)`(`origin`は`GeminiClient.SourceOrigin`の`WEB_SEARCH`/`URL_CONTEXT`)のリストとして`GeminiClient.Result.Success.sources`に含めます。抽出はすべて`opt*`系のみを使うため、フィールド名の解釈を誤っていても例外にはならず出典が空になるだけで応答本文自体は失われません。`sourceLabel()`(`MainActivity.kt`内)が各出典を「出典: タイトル」の形でラベル化します。`GeminiClient.encodeSources`/`decodeSources`で`Task.aiCachedSources`(JSON配列文字列、例`[{"title":"...","uri":"...","origin":"WEB_SEARCH"}]`)との相互変換を行い、`ReminderReceiver`は`taskDao.updateAiCachedResponse(taskId, response, sources)`で応答本文とあわせてキャッシュします。Googleの利用規約上、Search grounding利用時は出典(検索候補)の表示が求められますが、通知(`NotificationCompat.BigTextStyle`)はプレーンテキストのみのためリンク付きのHTML表示ができず、**出典は`TaskDetailDialog`(確認画面)・`GeminiTestDialog`にのみクリック可能なリンクとして表示し、通知本文には含めません**。`TaskViewModel.updateTask`は`aiPrompt`に加えこの2つのツール設定が変わった場合も`aiCachedResponse`/`aiCachedSources`を`null`にクリアします(条件が変われば古い結果・出典を使い回さないため)。バックアップのJSON形式にも`aiUseWebSearch`/`aiUseUrlContext`/`aiCachedSources`が含まれ、旧形式のファイルには無いキーのため`optBoolean`(既定`false`)・`isNull`で後方互換を保っています。Web検索の組み込みツールは通常のトークン課金とは別に無料枠が設定されていますが、モデル・料金プラン(無料/有料)によって条件が異なり、Geminiの料金体系自体も変わりやすいため、具体的な数値をハードコードせず設定画面の「AI連携」セクションでは「無料枠を超えると課金が発生するので[Gemini APIの料金ページ](https://ai.google.dev/gemini-api/docs/pricing)で確認すること」とだけ注記しています。**マップ(`google_maps`)は使用不可**: 地図データを使う用途が無いため、Gemini APIの組み込みツール`google_maps`によるグラウンディングは使用不可にしています。`EditTaskDialog`・`GeminiTestDialog`の`AiToolCheckboxes`にマップの選択肢は無く、`GeminiClient.generateContent`も`useMaps`引数自体を受け付けません(組み合わせ制約だった`MODELS_WITHOUT_SEARCH_AND_MAPS_COMBO`も、対応するツール自体が無くなったため削除済み)。`Task.aiUseMaps`カラムは既存端末のデータ・バックアップとの互換性のためだけに残しており、UIから`true`にする経路は無く、`TaskViewModel.updateTask`はタスクを保存するたびに(このマップ使用不可より前に`true`で保存されていたタスクを含め)`aiUseMaps`を`false`に正規化し、そのタスクのAI応答キャッシュ(`aiCachedResponse`/`aiCachedSources`)も古い条件のものとしてクリアします。`GeminiClient.SourceOrigin`にも`MAPS`は存在しません(過去に保存された`aiCachedSources`に`"origin":"MAPS"`が残っていた場合、`decodeSources`は不明な`origin`として`WEB_SEARCH`扱いにフォールバックします)。

## 位置情報リマインダー

**位置情報リマインダー**: `com.google.android.gms:play-services-location`(`app/build.gradle.kts`に追加。`google()`リポジトリ経由なので既存のAndroidX依存と同じくローカルサンドボックスでは解決できずGitHub Actionsでのみビルド確認可能)のGeofencing APIを使い、期限日時リマインダーとは独立した別機能として実装しています。`EditTaskDialog`の「位置」セクションで、住所文字入力(`geocodeAddress()`、`LocationLookup.kt`内のトップレベル関数。`android.location.Geocoder`を使い、位置情報の権限は不要)または「現在地を使う」ボタン(`getCurrentLocationResult()`、同ファイル内。`FusedLocationProviderClient.getCurrentLocation`を使い、`ACCESS_FINE_LOCATION`権限が必要)のいずれかで場所を1件登録し、半径(100m/300m/500m/1km)と通知タイミング(到着時・離脱時をタスクごとに個別選択、両方も可)を設定します。位置が未設定なら通知タイミングも未設定のままで良い一方、位置を設定した場合は到着・離脱のどちらか一方以上を選ばないと保存ボタンが無効化されます。`notification/LocationReminderManager`(`register`/`unregister`)がジオフェンス(requestId=タスクIDの文字列表現)の登録・解除を担当し、`TaskViewModel`の`updateTask`・`toggleDone`(繰り返しタスクの次回生成分を含む)・`deleteTask`、および`TaskCompletion.complete`から呼び出されます。ジオフェンスの登録には`ACCESS_FINE_LOCATION`に加えAPI 29(Q)以降は`ACCESS_BACKGROUND_LOCATION`も必要で(`LocationReminderManager.hasLocationPermission`で両方を確認)、権限が無ければ登録をスキップします。位置情報を使うタスクが1つ以上あるのに権限が不足している場合、メイン画面に権限バナーを表示し、タップすると`Settings.ACTION_APPLICATION_DETAILS_SETTINGS`でアプリ設定画面へ誘導します(この画面から「常に許可」を選べば両方の権限が一度に付与されます)。`notification/GeofenceReceiver`が到着・離脱イベントを受け取ります。**通知のデバウンス**: GPS/ネットワーク測位の精度が低いタイミングでは、実際には動いていなくてもジオフェンスの内外判定が一瞬だけ反転し、ENTER/EXITが誤って発火することがあります(特に半径に対して精度〈`Location.accuracy`〉が粗い場合や、複数のジオフェンスの円が近接・重複している場合に起きやすい)。これを避けるため、`GeofenceReceiver`はイベントを受け取っても即座に通知せず、対象タスクが未完了かつそのタスクが該当する遷移方向を望んでいる場合に限り`GeofenceConfirmWorker.schedule(context, taskId, isEnter)`を呼んでデバウンスします。`GeofenceConfirmWorker`(`CoroutineWorker`)は`WorkManager.enqueueUniqueWork`を`ExistingWorkPolicy.REPLACE`・ユニークワーク名`"geofence_confirm_<taskId>"`で使うため、同じタスクに対してデバウンス時間内(既定`GeofenceConfirmWorker.DEBOUNCE_DELAY_MINUTES`=3分)に別のイベント(同方向・反対方向を問わず)が届くと、以前の実行はキャンセルされ新しいイベントのタイマーに置き換わります。つまり実際に通知が確定するのは「最後に受信したイベントから3分間、後続のイベントが来なかった」場合のみで、`doWork`実行時にタスクの状態(完了済みでないか・通知タイミングを希望しているか)を再確認してから、期限日時通知とは別の通知チャンネル`location_reminders`で通知を表示する処理(`notification/LocationReminderNotifier.showNotification`、`GeofenceReceiver`から切り出した共通処理)を呼びます(通知IDは期限日時通知〈`ReminderReceiver`〉と同じ`taskId.toInt()`を使いますが、通知タグは別〈`NOTIFICATION_TAG_LOCATION`、詳細は前項〉のため、同じタスクに期限日時リマインダーも設定されていて両方が発火しても、互いを上書きせず両方とも通知欄に表示されます。「完了」ボタン〈`CompleteReceiver`〉はどちらの通知でも正しく消去できます)。ジオフェンスは端末再起動で失われるため、`BootReceiver`が`taskDao.getPendingWithLocation()`の全件を`LocationReminderManager.register`で再登録します。バックアップのJSON形式にも位置情報の各フィールドが含まれます。`GeofencingRequest`の`initialTrigger`は「到着時」が有効な場合のみ`INITIAL_TRIGGER_ENTER`を指定しており、登録した時点で既に圏内にいればすぐに通知が届くため動作確認がしやすくなっています(離脱のみの場合は初回トリガー無し)。ジオフェンスは完了・削除・位置設定の解除以外では解除されないため、エリア外→エリア内を繰り返すたびに何度でも通知される設計です(1回きりの通知ではありません)。ただしGeofencing APIのデフォルトの通知応答性は数分単位と粗く、特に小さい半径ではGPS誤差でEXITが検知されずその後のENTERも漏れることがあるため、`GeofencingRequest.Builder.setNotificationResponsiveness()`で`NOTIFICATION_RESPONSIVENESS_MILLIS`(60秒)を指定し、再突入の検知を速めています。`addGeofences`の成功/失敗、および`GeofenceReceiver`が実際に受信したジオフェンスイベント(ENTER/EXITの種別・対象requestId・デバウンス予約の可否)は`Log`(タグ`LocationReminder`)に出力するので、繰り返し通知されない場合はlogcatで「イベント自体が来ていないのか」「来ているが条件(完了済み/通知タイミング未選択)で弾かれているのか」「デバウンス中に反対方向のイベントで打ち消されたのか」を切り分けられます。設定画面(`SettingsScreen`)の「位置情報デバッグ」ボタンから`LocationDebugDialog`を開くと、位置情報の権限状態(前面/常に許可)、「現在地を取得」ボタンによる現在地の座標、位置情報を設定した各タスクの登録座標・半径・通知タイミング・現在地からの距離と圏内/圏外を確認できます(実際にOS側へ登録済みかどうかを直接問い合わせるAPIは無いため、あくまでタスクのフィールド値と権限状態から推測した表示です)。

## 位置情報リマインダーの確認方式(連続追跡)

**位置情報リマインダーの確認方式**: Geofencing APIは内部の評価間隔を端末側で間引くことがあり、実際には数時間前に起きていた遷移がまとめて(複数タスク同時に)遅れて通知される「遅延キャッチアップ」が起こりうるため、これを避けたいユーザー向けに、Geofencing APIとは別のもう1つの確認方式として**連続追跡方式**を選択できます。`notification/LocationTrackingMode`(`GEOFENCING_API`/`CONTINUOUS_TRACKING`)と`notification/LocationTrackingSettings`(SharedPreferences`location_tracking_settings`。モードと更新間隔〈分、`MIN_INTERVAL_MINUTES`=1〜`MAX_INTERVAL_MINUTES`=60、既定`DEFAULT_INTERVAL_MINUTES`=15に丸める〉を永続化)で表し、アプリ全体で共通の設定です(タスクごとの個別設定ではありません)。設定画面(`SettingsScreen`)の「位置情報」セクションで`FilterChip`による方式選択と、連続追跡方式選択時のみ表示される更新間隔の入力欄(分、保存ボタンで確定)を提供します。`notification/LocationReminderManager`の`register`/`unregister`は`LocationTrackingSettings.getMode`で分岐し、Geofencing APIモードでは従来どおりジオフェンスを登録する一方、連続追跡方式では`notification/LocationTrackingService`(フォアグラウンドサービス、`android:foregroundServiceType="location"`、`FOREGROUND_SERVICE`・`FOREGROUND_SERVICE_LOCATION`権限が必要)を起動します。`LocationTrackingService`は`FusedLocationProviderClient.requestLocationUpdates`で設定した間隔を希望値として位置の更新を要求し(`LocationRequest.Builder`の`intervalMillis`/`setMinUpdateIntervalMillis`。端末やシステムの状態によっては実際の更新がそれより遅れることがあります)、`taskDao.getPendingWithLocation()`の全件それぞれについて`metersBetween()`で距離を計算し圏内/圏外を判定、前回評価時の状態を`data/GeofenceState`(`taskId`/`isInside`/`latitude`/`longitude`/`radiusMeters`、`AppDatabase`バージョン15→16の`MIGRATION_15_16`で追加した`geofence_states`テーブル。プロセス再起動を挟んでも基準を見失わないようRoomに永続化)と比較して遷移を検知します(初回評価時はGeofencing APIの`INITIAL_TRIGGER_ENTER`と同様、既に圏内かつ到着通知希望の場合のみ即座に扱う)。`latitude`/`longitude`/`radiusMeters`は、記録した`isInside`がどのジオフェンス定義(位置・半径)に基づく評価結果かを表す。`LocationReminderManager.register`はタスクの編集(位置・半径と無関係な項目の変更を含む)のたびに呼ばれるため、記録済みの定義がタスクの現在の設定と一致する場合は基準値をそのまま保持し(無駄な初回評価扱いによる到着通知の再送を避ける)、位置・半径が実際に変わった場合のみ削除して次回評価を初回評価扱いにする。`LocationTrackingService.evaluateTask`側でも同様の一致確認を行い、万一削除し損ねた基準値が残っていても誤判定しないようにしている。遷移を検知した後の処理はGeofencing APIモードと共通で、`GeofenceReceiver`と同じ`GeofenceConfirmWorker.schedule()`(3分デバウンス)に合流させ、位置情報の更新履歴(後述)にも`〈連続追跡〉`のdetail付きで記録します。`LocationReminderManager.switchMode(context, newMode)`は方式切り替え時に旧方式のリソース(Geofencing APIなら共有`PendingIntent`単位での全ジオフェンス一括解除、連続追跡方式ならサービス停止+`geofence_states`全削除)を解除してから新方式で`reconcileAll`(位置情報を使う未完了タスクの再登録)を行い、`updateContinuousTrackingInterval(context, minutes)`は間隔変更時にサービスが動作中であれば再起動して即座に新間隔を反映します。`BootReceiver`は引き続き`LocationReminderManager.register`経由で呼ぶため、モードを意識せず端末再起動後の再登録が両方式に対応します。**排他制御**: `register`/`unregister`/`switchMode`/`reconcileAll`/`updateContinuousTrackingInterval`はいずれも`LocationReminderManager`が持つ単一の`Mutex`で直列化しています。これらは複数の独立したコルーチン(`TaskViewModel`の各操作・`BootReceiver`・設定画面からの確認方式/更新頻度変更)から並行に呼ばれうるため、直列化しないと例えば確認方式の切り替え中に古い`updateContinuousTrackingInterval`呼び出しが完了して停止直後のサービスを再起動してしまう、といった順序崩れが起こりえます。内部的には各公開関数がロックを取得したうえで`registerLocked`等の非公開実装に委譲し、`reconcileAll`から`register`を呼ぶ場合のように関数間で連鎖する処理は非公開実装同士を直接呼び合うことで同じロックの二重取得(デッドロック)を避けています。Geofencing APIモードの`addGeofences`/`removeGeofences`はPlay services側で非同期の`Task`を返すため、`registerGeofencingApi`/`unregisterLocked`/`switchMode`はいずれも`awaitCompletion()`(`suspendCancellableCoroutine`+`addOnCompleteListener`によるブロッキングしない待ち合わせ)でその完了までロックを保持し続けます。これを怠ると、例えば確認方式をGeofencing API→連続追跡→Geofencing APIと短時間で往復させた際に、最初の解除処理の完了が2回目の再登録より後になり、せっかく登録し直したジオフェンスを消してしまうことがあるためです。`awaitCompletion()`自体は`withContext(NonCancellable)`で包み、呼び出し元のコルーチン(`TaskViewModel.viewModelScope`や`MainActivity`の`rememberCoroutineScope`)が途中でキャンセルされてもこの待ち合わせ(=ロックの保持)だけは中断されないようにしています(そうしないと発行済みのTaskが完了しないままロックだけ解放され、直列化が崩れるため)。また`LocationTrackingService`は`onLocationResult`から直接評価用コルーチンを起動するのではなく、`Channel<Location>`(`CONFLATED`。評価〈Room読み書き・ワーカー予約・ログ書き込みを含む〉が設定間隔より時間がかかってコンシューマーが遅れても、未処理の位置情報が無制限に溜まり続けないよう、最新の1件のみ保持し古いものは破棄する)に`trySend()`で積むだけに留め、`onCreate`で1つだけ起動する単一のコンシューマーコルーチンが順に`for (location in locationChannel)`で取り出して評価します(`scope.launch`を毎回呼ぶ方式だと、コルーチンの起動自体は非同期なため開始順序がコールバックの到着順と入れ替わりうるが、`trySend`は同期的にキューへ積むだけなので到着順がそのまま処理順になる)。このコンシューマーは`SupervisorJob`配下で動作しますが、`handleLocation`(Room操作・`GeofenceConfirmWorker.schedule`等を含む)が`CancellationException`以外の例外を投げた場合にループ自体を抜けて終了してしまうと、`SupervisorJob`のおかげで親の`scope`は無事でもこのコンシューマー自身は二度と再開せず、以後受信する位置情報が一切評価されなくなってしまいます。これを避けるため、`for`ループ内で`handleLocation`呼び出しを`try`/`catch`し、`CancellationException`は再送出する一方それ以外の例外はログに残して次の位置情報の処理を続けます(1件の評価失敗でコンシューマー全体を道連れにしない)。**停止完了バリア**: `LocationTrackingService`の`companion object`が持つ`consumerJob`(`Job?`、コンシューマーコルーチン自身への参照。`onCreate`で`scope.launch { ... }`の戻り値を代入)と`stopAndAwaitCompletion(context)`は、「新しい位置の受信を止め、キュー済みの評価も含めてコンシューマーコルーチンが完全に終了する」ことを待ち合わせる仕組みです。`stopAndAwaitCompletion`は`Context.stopService`を呼んだ後、保持しておいた`consumerJob`を`Job.join()`で直接待ちます(`consumerJob`が`null`、すなわちサービスが一度も起動していなければ即座に戻ります)。`Context.stopService`の戻り値(サービスが元々動作していたか)は判定に使いません。既に別経路でサービスの停止処理が始まっていると`stopService`が`false`を返す一方、`consumerJob`自体は`handleLocation`の途中でまだ実行中のことがあり、この戻り値で早期リターンすると`evaluateTask()`が`GeofenceStateDao.upsert()`する前に呼び出し元が`deleteAll()`してしまい削除したはずの状態が復活するため、`consumerJob`が非nullなら戻り値に関わらず必ず`join()`します。`Job.join()`は対象のJobが既に終了済み(正常・異常・キャンセルいずれの場合も)であれば即座に戻り、まだ実行中であれば終了まで中断して待つため、`stopAndAwaitCompletion()`が呼ばれるより前に`handleLocation`内の例外でコンシューマーコルーチンが先に異常終了していた場合でも取りこぼさず正しく完了を検知できます(以前は`CompletableDeferred`+`invokeOnCompletion`方式でしたが、`stopAndAwaitCompletion()`呼び出し前にJobが既に終了していると、後から設定した`CompletableDeferred`はそのJobから二度と`invokeOnCompletion`が呼ばれず永久に完了しない不具合がありました)。`stopAndAwaitCompletion`自体も`withContext(NonCancellable)`で包んでおり(`LocationReminderManager.awaitCompletion()`と同じ考え方)、呼び出し元(`LocationReminderManager.switchMode`、ひいては`TaskViewModel.viewModelScope`)が待機中にキャンセルされてもこの停止要求と待ち合わせは中断されません。`LocationReminderManager.switchMode`が連続追跡方式から離れる際は`LocationTrackingService.stopAndAwaitCompletion(context)`の完了後に`geofenceStateDao().deleteAll()`を呼ぶことで、評価中・キュー済みだった書き込みが削除より後に発生して復活してしまう競合を防いでいます(`onDestroy`側は評価がまだ途中でも`job`を`cancel`せず、コンシューマーコルーチンが自然に`for`文を抜けるのに任せることで、キュー済みの最後の要素の処理が完了バリアの前に打ち切られないようにしています)。`switchMode`の本体は`lifecycleMutex.withLock`の内側で丸ごと`withContext(NonCancellable)`にも包んでいます。`stopAndAwaitCompletion()`/`awaitCompletion()`自体は個別にNonCancellableで保護済みですが、それらの完了直後や`setMode()`・`reconcileAllLocked()`の実行中に呼び出し元(`TaskViewModel.viewModelScope`等)がキャンセルされると、旧方式のリソースは解除済みなのに新方式への切り替え(モードの保存・再登録)が完了しないまま処理が中断され、どちらの方式でも位置情報が機能しない不整合な状態が残ってしまうためです。また`LocationTrackingService.onStartCommand`は、位置情報の権限確認に加えて`LocationManagerCompat.isLocationEnabled()`で端末側の位置情報サービス(設定アプリの「位置情報」トグル)が有効かどうかも確認してから`startForeground`を呼びます。権限があっても位置情報サービス自体がオフの場合、Android 14以降は`foregroundServiceType="location"`の`startForeground`が`SecurityException`を投げるため、権限確認だけでは検知できないこのケースを別途弾いています(無効なら`stopSelf()`+`START_NOT_STICKY`)。さらに`startForeground`の直後、`EXTRA_FORCE_RESTART`の処理より前に`LocationTrackingSettings.getMode(this)`を読み直し、`CONTINUOUS_TRACKING`でなければ`stopSelf()`+`START_NOT_STICKY`で停止します。`updateContinuousTrackingInterval`が発行した`restart()`のIntentは配送されるまでに`switchMode()`で確認方式がGeofencing APIへ切り替わり永続化されていることがあり、このモード再確認が無いと、既に選ばれていない連続追跡方式のまま`EXTRA_FORCE_RESTART`を処理して位置情報の購読を開始してしまいます。

## 位置情報の更新履歴(デバッグ)

**位置情報の更新履歴(デバッグ)**: `data/LocationUpdateLog`(`id`/`timestamp`/`type`〈`data/LocationUpdateType`の`ENTER`/`EXIT`/`PERIODIC`〉/`taskTitle`〈ENTER/EXITの場合のみ設定〉/`latitude`/`longitude`/`accuracy`/`detail`/`distanceMeters`・`radiusMeters`〈いずれもENTER/EXITの場合のみ設定、任意〉)として、ジオフェンスのENTER/EXITイベント受信と定期的な現在地取得の両方を記録します(`LocationUpdateLogDao`、`AppDatabase`バージョン12→13の`MIGRATION_12_13`、`distanceMeters`/`radiusMeters`はバージョン14→15の`MIGRATION_14_15`で追加)。`GeofenceReceiver`はデバウンス予約の可否に関わらず(タスクが見つからない/完了済み/通知タイミング未選択、いずれの場合も)ENTER/EXITイベントを受信するたびに1件記録し`detail`に理由を残すため、「イベント自体が来ていないのか」「来ているが条件で弾かれているのか」をlogcat無しでアプリ内(位置情報デバッグ画面)から切り分けられます。**`distanceMeters`/`radiusMeters`**は、そのイベントの`triggeringLocation`(タスクが見つからない・座標未登録なら`null`)からタスクに登録された座標までの距離とそのタスクの`radiusMeters`をそのまま記録したもので、例えば「距離8m/半径15m」のEXITであれば実際には圏内のままGPS/ネットワーク測位の誤差でEXITが誤検知されたと、`LocationDebugDialog`内の「更新履歴」セクション(`LocationUpdateLogRow`、距離・半径から「圏内」「圏外」も表示)から直接判別できます。距離計算自体は`LocationLookup.kt`のトップレベル関数`metersBetween()`(`android.location.Location.distanceBetween`のラッパー)に共通化しており、`GeofenceReceiver.distanceToTask`と`LocationDebugDialog`内の「現在地からの距離」表示の両方から使っています。ただし実際に通知したかどうかはこのログには残らず(`GeofenceConfirmWorker`がデバウンス確定後に通知履歴〈`NotificationLog`、後述〉へ記録する)、`detail`が`"受信(3分後も継続していれば通知)"`のイベントがデバウンス中に反対方向のイベントで置き換えられた場合、そのまま通知されずに終わることがあります。加えて、`notification/LocationUpdateWorker`(`CoroutineWorker`)が`notification/LocationUpdateScheduler`経由で5分間隔の自己連鎖する`OneTimeWorkRequest`として動作し、位置情報を使う未完了タスクがある間だけ現在地を1回取得して`type = PERIODIC`で記録します(WorkManagerの`PeriodicWorkRequest`は最短でも15分間隔までしか指定できないため、より短い間隔で記録できるよう`LocationUpdateWorker`が実行完了のたびに`LocationUpdateScheduler.scheduleNext`〈`ExistingWorkPolicy.REPLACE`〉で次回分を予約する自己連鎖にしています。`LocationReminderManager.register`が位置情報タスクを登録するたびに`LocationUpdateScheduler.ensureScheduled`〈`ExistingWorkPolicy.KEEP`〉を呼んで連鎖を起動し、既に動作中なら何もしません。位置情報を使うタスクが無くなった場合は`LocationUpdateWorker`が次回分を予約せずに終わることで連鎖が自然に停止するため、停止までに最大5分の遅延があります。`PeriodicWorkRequest`と異なりWorkManagerが自動的に再実行してくれるわけではないため、`LocationUpdateWorker.doWork()`は位置情報タスクが残っている間の処理を`try`/`finally`で囲み、途中で例外が発生した場合でも必ず次回分を予約して連鎖が途切れないようにしています)。`LocationUpdateLogDao.insertAndTrim(log, retentionMillis)`(デフォルト6時間)が記録のたびに直近6時間より古い履歴を自動削除します。`TaskViewModel.locationUpdateLogs: StateFlow<List<LocationUpdateLog>>`(発生時刻の降順)として公開し、`LocationDebugDialog`内の「更新履歴」セクション(`LocationUpdateLogRow`)が新しい順に一覧表示します。バックアップのエクスポート/インポート対象には含めていません(通知履歴と同様、デバッグ用の実行時ログのため)。

## 通知履歴(デバッグ)

**通知履歴(デバッグ)**: `data/NotificationLog`(`id`/`triggeredAt`〈発動時刻、epoch millis〉/`taskTitle`〈発動時点のタスクタイトル〉/`triggerCondition`〈トリガとなった条件を表す文字列〉)として、実際に発火した通知の履歴を記録します(`NotificationLogDao`、`AppDatabase`バージョン11→12の`MIGRATION_11_12`)。記録対象は期限日時通知(`ReminderReceiver`。通常の期限到達は`triggerCondition = "期限到達"`、`ReminderScheduler.scheduleSnooze`経由のスヌーズ再通知は`"スヌーズ経由の再通知"`)と位置情報通知(`GeofenceReceiver`。到着/離脱と保存済みの場所名・半径を含む文字列)で、いずれも通知を実際に表示した直後に記録します。テスト通知(`ReminderScheduler.scheduleTestNotification`)は記録対象外です。`ReminderScheduler`の`pendingIntentFor(context, taskId, isSnooze)`は`EXTRA_IS_SNOOZE`をIntentのextraとして持たせており、`schedule`(通常)/`scheduleSnooze`(スヌーズ)のどちらが最後に呼ばれたかで`ReminderReceiver`が発火理由を判定します(`PendingIntent.FLAG_UPDATE_CURRENT`により同じtaskId=同じrequestCodeのPendingIntentのextrasが都度上書きされる)。`NotificationLogDao.insertAndTrim(log, limit = 200)`(Kotlinのデフォルトメソッド+`@Transaction`)が挿入のたびに直近200件を超える古い履歴を自動削除し、無制限にDBが肥大化しないようにしています。`TaskViewModel.notificationLogs: StateFlow<List<NotificationLog>>`(発動時刻の降順)として公開し、設定画面の「通知履歴」ボタンから開く`NotificationLogDialog`が新しい順に一覧表示します。バックアップのエクスポート/インポート対象には含めていません(デバッグ用の実行時ログであり、復元して意味のあるデータではないため)。

## 保存済みの場所

**保存済みの場所(自宅・職場など)**: `data/SavedLocation`(`id`/`name`/`latitude`/`longitude`/`radiusMeters`)として、タスクとは独立に登録しておける場所の一覧です。設定画面(`SettingsScreen`)の「場所を編集」ボタンから`ManageLocationsDialog`を開くと、住所文字入力または現在地取得(`LocationPicker`、後述)で座標を決めてから名称・半径を付けて登録でき、登録済みの一覧では名称のタップで名称・半径の変更(座標は変更不可。座標を変えたい場合は削除して登録し直す)、「削除」ボタンで削除できます。`EditTaskDialog`の「位置」セクションは「住所で指定」「現在地を使う」に加えて「登録済みから選択」タブを持ち、選択すると保存済みの場所がチップとして並び、タップするとそのタスクの位置・半径にそのまま反映されます(反映後も半径チップで上書き可能)。「住所で指定」「現在地を使う」の入力UI自体は`LocationPicker`(`MainActivity.kt`内のプライベートComposable)として`EditTaskDialog`と`ManageLocationsDialog`で共通化しています。バックアップのJSON形式にも`savedLocations`配列として含まれます(旧形式のファイルにはキー自体が無いため、`JSONObject.optJSONArray`で無ければ空扱いにして後方互換を保っています)。

## タスクのURL・メモ

**タスクのURL・メモ**: `Task.url`/`Task.memo`はいずれも任意の文字列で、`EditTaskDialog`のタイトル直下(URL)・サブタスク一覧の直前(メモ、複数行の`OutlinedTextField`)で入力・編集できます。`url`はダイアログ保存時に`normalizeUrl()`(`MainActivity.kt`内のプライベート関数)で先頭が`http://`/`https://`でなければ`https://`を補い、空文字ならNULLとして保存します。`url`が設定されている場合、期限日時通知(`ReminderReceiver`)・位置情報通知(`GeofenceReceiver`)の両方に「リンクを開く」という`NotificationCompat.Action`が追加され、タップすると`ReminderScheduler.openUrlPendingIntent(context, taskId, url)`が`Intent.ACTION_VIEW`でブラウザ等を起動します(通知本体のタップは従来どおりアプリを開きます)。このボタンの`PendingIntent`リクエストコードは`taskId.toInt() * 10 + 9`で、「スヌーズ」ボタンの`taskId.toInt() * 10 + 5`(詳細は前項)と衝突しないオフセットを使っています。`memo`は通知には表示されず、`EditTaskDialog`を開いたときのみ参照・編集できます。

## タスクへのファイル添付

**タスクへのファイル添付**: ## ローカルバックアップ(エクスポート/インポート)

**ローカルバックアップ(エクスポート/インポート)**: `app/src/main/java/com/toshi0907/oboetotte/backup/BackupManager.kt`が実体です。エクスポート形式はZIP(`oboetotte_backup_*.zip`)で、`backup.json`エントリに従来どおりのJSON構造(`{"version":2,"exportedAt":<epoch millis>,"lists":[...],"tasks":[...],"savedLocations":[...],"attachments":[...]}`。`lists`/`tasks`/`savedLocations`/`attachments`はそれぞれ`TaskList`/`Task`/`SavedLocation`/`TaskAttachment`の全フィールドをそのまま含む)、`attachments/<storedFileName>`エントリに添付ファイルの実体を格納します。インポート側は`org.json.JSONObject.isNull`がキー自体が存在しない場合も`true`を返す仕様を利用しており、`repeatDaysOfWeek`・`url`・`memo`・`seriesId`・`savedLocations`・`attachments`キーを含まない旧形式のバックアップファイルもエラーなく読み込めます。ZIPかどうかの判定はファイルの拡張子やMIMEタイプではなく、読み込んだバイト列先頭のZIPマジックナンバー(`PK\x03\x04`)を見て行っており(`BackupManager.isZip`)、添付機能追加前のプレーンJSON形式のファイルもそのまま読み込めます(標準ライブラリの`org.json`・`java.util.zip`のみを使用し、追加のシリアライズ用依存は入れていません)。`BackupManager.export(context, uri)`/`import(context, uri)`はいずれも`Dispatchers.IO`上で実行し、Roomの`taskListDao().getAll()`等を`Flow.first()`で1回だけ取得してZIPとして`ContentResolver`経由で書き出す/逆に読み込んでパースします。インポートは追記ではなく全置き換えです(`id`/`listId`/`parentTaskId`/`taskId`の対応関係を維持するため)。**インポートの安全性**: バックアップファイルは端末外で作られたZIP/JSONを信頼できない入力として扱い、既存データの削除より前に検証を済ませます。`AttachmentStorage.file()`はZIPエントリ名・JSON側の`storedFileName`のどちらについても単一ファイル名であること(パス区切りを含まない)と正規化後のパスが必ず`attachments`ディレクトリ直下に収まることを検証し、パストラバーサル(`../`等で`filesDir/attachments/`の外を指す値)を拒否します。また添付ファイルのメタデータ(JSON側の`attachments`配列)とZIPエントリの実体が過不足なく1対1で対応していることも検証し、一致しなければインポート全体を中断します。これらの検証をすべて通過した後、添付ファイルの実体をまず一時ディレクトリ(`filesDir/attachments_import_staging/`)へ書き込みます(ディスク容量不足等のI/O失敗はここで起きるため、失敗すれば既存のDB・添付ファイルには一切触れずに済みます)。全件の書き込みが成功した後、本来の`attachment/AttachmentStorage`のディレクトリを`filesDir/attachments_import_backup/`へ`renameTo`で退避し、一時ディレクトリを本来のディレクトリ名へ`renameTo`で入れ替えます(いずれもファイル単位ではなくディレクトリ単位の`renameTo`のみで、実体のコピーを伴わないため失敗の余地が小さい。`renameTo`は戻り値でしか失敗を通知しないため必ず確認し、失敗した場合は退避しておいたディレクトリを元の名前に戻します)。DBとファイルシステムは別々のリソースで単一のトランザクションにはできないため、**添付ディレクトリの入れ替えをDB更新より先に行う**順序にしており、`TaskDao`/`TaskListDao`/`SavedLocationDao`/`TaskAttachmentDao`の`deleteAll()`+`insertAll()`をRoomの`AppDatabase.withTransaction { }`でアトミックに置き換えるのは最後です。こうすることで、より失敗しやすいDB更新の方を最後にでき、DB更新が失敗した場合(Room側で自動的にロールバックされる)は直前で入れ替えたディレクトリも明示的に元へ戻します。これにより、検証・ファイル書き込み・ディレクトリの入れ替え・DB更新のいずれの段階で失敗しても、既存のDB・添付ファイルは基本的に元のまま残ります。UI側はメイン画面の「設定」`AssistChip`から遷移する設定画面(`SettingsScreen`、`MainActivity.kt`)の「バックアップ」セクションが導線で、実際のファイル選択は`MainActivity`に登録した`ActivityResultContracts.CreateDocument("application/zip")`(エクスポート)と`ActivityResultContracts.OpenDocument()`(インポート、mime `*/*`。上記の通り実際の形式判定は内容で行うため)というStorage Access Frameworkの標準コントラクトで行います。DAOの`getAll()`はRoomの`Flow`なので、インポート後の`deleteAll`/`insertAll`による変更も既存の`StateFlow`購読(`TaskViewModel`)へ自動的に反映され、画面の再起動は不要です。

## クラウド自動バックアップ

**クラウド自動バックアップ**: 上記のローカルバックアップとは別に、Storage Access Framework(SAF)で選択したフォルダへ毎日1回自動でZIPバックアップする機能です。Dropbox・Google Drive・OneDrive等、SAFのドキュメントプロバイダとして自身を公開しているクラウドストレージアプリがインストールされていれば、標準のフォルダ選択ダイアログからそのアプリ内のフォルダを保存先に選べるため、Dropbox APIのようなアプリ固有のAPIキー取得・OAuth認証の実装は一切不要です(選んだフォルダへの書き込みは、そのフォルダを提供しているアプリ自身がクラウドへの同期を担います)。`backup/CloudBackupSettings`(SharedPreferences`cloud_backup_settings`。有効/無効・保存先フォルダのツリーURI・保持件数〈`MIN_RETENTION_COUNT`=1〜`MAX_RETENTION_COUNT`=90、既定`DEFAULT_RETENTION_COUNT`=7〉・保存時刻〈時・分、既定`DEFAULT_BACKUP_HOUR`=3時`DEFAULT_BACKUP_MINUTE`=0分〉・最終実行時刻/結果〈`CloudBackupResult`の`SUCCESS`/`FAILURE`〉を永続化)、`backup/CloudBackupRunner.run(context)`(実処理。`BackupManager.export`と同じ内容のZIPをまず端末内の一時ファイル〈`context.cacheDir`〉へ書き出し、これが成功した場合のみ保持件数-1件になるまで古いファイルを`pruneOldBackups`で削除し、日時付きファイル名`oboetotte_cloud_backup_*.zip`で`DocumentFile.createFile()`により保存先フォルダへ新規作成した上でその一時ファイルの内容をコピーし、結果を`CloudBackupSettings.recordResult`へ記録する。この順序〈エクスポート成功の確認→古いファイルの削除→保存先への作成・コピー〉には2つの意図がある。まず、新規ファイルの作成・書き込みを先に行い削除を後回しにすると、保持件数ちょうどの状態から次のバックアップを取る際に一時的に保持件数+1件分の保存領域が必要になり、保存先の空き容量やクォータが保持件数ちょうどしか無い場合〈保持件数の上限に達している場合〉に失敗してしまう。一方、古いファイルの削除をZIPの書き出し(DBの読み込み・ZIP生成、端末のローカルストレージのみを使うため保存先フォルダの空き容量・クォータには影響しない)の成否が分かる前に行うと、書き出し自体が失敗した際に古いバックアップを削除しただけで新しいものが用意できず、既存のバックアップを失ってしまう。ZIPの書き出しを先に済ませ、それが確実に成功した後にだけ保存先フォルダの古いファイルを削除することで、この失敗パターンは避けている(なお、削除後の保存先への新規ファイル作成・コピー自体がネットワークエラー等で失敗した場合は、その回に限り保持件数より1件少ない状態になりうるが、これは保存先の容量が保持件数ちょうどしか無い状況で新規ファイルを追加する以上、原理的に避けられないトレードオフである)。ローカルバックアップの手動エクスポート〈後述、ファイル名`oboetotte_backup_*.zip`〉と意図的に異なるプレフィックスにしており、ユーザーが手動エクスポートの保存先として同じクラウドフォルダを選んでも、保持件数超過分の削除〈`pruneOldBackups`〉が手動エクスポートしたファイルを巻き込んで削除してしまわないようにしている)、`backup/CloudBackupWorker`(`CoroutineWorker`。`backup/CloudBackupScheduler`が`PeriodicWorkRequest`で24時間間隔にスケジュールし、`CloudBackupRunner.run`を呼ぶだけ。保存先はDropbox等のアプリ自身が同期を担うためネットワーク接続を制約条件にしていません)で構成されています。設定画面(`SettingsScreen`)の「クラウド自動バックアップ」セクションから、`ActivityResultContracts.OpenDocumentTree()`(`MainActivity`の`selectCloudBackupFolderLauncher`)でフォルダを選択すると`TaskViewModel.setCloudBackupFolder(uri)`が`ContentResolver.takePersistableUriPermission()`で書き込み権限を永続化してから保存し(アプリ・端末の再起動を越えて有効)、`FilterChip`で自動バックアップの有効/無効を切り替えられます(有効化は保存先フォルダが未設定だと`TaskViewModel.setCloudBackupEnabled`内で無視されます)。有効化は`CloudBackupScheduler.reschedule`、無効化は`cancel`を呼びます。`reschedule`(`ExistingPeriodicWorkPolicy.REPLACE`)は現在の保存時刻設定(`CloudBackupSettings.getBackupHour`/`getBackupMinute`)から「次に訪れるその時刻」までの遅延を計算し、`PeriodicWorkRequest`の初回遅延として指定し直すことで、既存の定期実行があってもその場で新しい時刻に合わせて再登録します(WorkManagerの定期実行は正確なアラームではないため、実際の発火時刻は多少前後します)。設定画面の「変更」ボタンから`TimePicker`(`AlertDialog`+`rememberTimePickerState`、期限日時の時刻選択と同じ部品)で保存時刻を選ぶと`TaskViewModel.setCloudBackupTime(hour, minute)`が設定を保存し、自動バックアップが有効化中であれば同じ`reschedule`を呼んで次回実行時刻に即座に反映します(無効化中は設定を保存するだけで、実際のスケジュール登録は次回有効化時に行われます)。`MainActivity`は起動のたびに`CloudBackupScheduler.ensureScheduled`(`ExistingPeriodicWorkPolicy.KEEP`)を呼び、(有効かつ保存先設定済みなのに)定期実行が何らかの理由で登録されていない場合にのみ現在の保存時刻設定で新規登録します(`AppUpdateCheckScheduler`と同様の保険的パターンで、既存の定期実行がある限り初回遅延は再計算されません)。「今すぐバックアップ」ボタンから`TaskViewModel.runCloudBackupNow`で定期実行と同じ処理を即座に1回行え、直近の実行結果(成功/失敗・実行時刻)も同じ画面に表示されます。`cloudBackupLastBackupAt`/`cloudBackupLastResult`は`CloudBackupSettings.recordResult`によるSharedPreferencesの変更を`SharedPreferences.OnSharedPreferenceChangeListener`(`TaskViewModel`の`init`で`CloudBackupSettings.addLastResultChangeListener`により登録、`onCleared`で解除)で直接購読して同期しており、`CloudBackupWorker`による定期実行の結果もアプリのプロセスが生きている間はアプリを再起動せず即座に画面へ反映されます(SharedPreferencesはリスナーをWeakReferenceでしか保持しないため、`TaskViewModel`側でリスナーをフィールドとして保持し続けています)。バックアップの対象データ・ZIP形式はローカルバックアップと完全に同一(`BackupManager.export`をそのまま再利用)で、復元(インポート)は引き続きローカルのZIPファイル選択(前述の`importBackupLauncher`)からのみ行う想定です(クラウド上のファイルであっても、端末のファイル選択ダイアログから選べば同じ`BackupManager.import`でインポートできます)。

## ホーム画面ウィジェット

**ホーム画面ウィジェット**: `app/src/main/java/com/toshi0907/oboetotte/widget/TaskWidget.kt`にJetpack Glance(`androidx.glance:glance-appwidget`。既存のAndroidX依存と同じく`google()`リポジトリ経由のためGitHub Actionsでのみビルド確認可能)で実装しています。`TaskWidget`(`GlanceAppWidget`)の`provideGlance`が毎回`AppDatabase.getInstance(context).taskDao().getAll().first()`で最新のタスク一覧を取得し、`parentTaskId == null && !it.isDone`でトップレベルの未完了タスクのみに絞り込んだ上で、後述の「表示するリスト」設定でさらに絞り込んで表示します(`TaskDao.getAll`の`ORDER BY`をそのまま使うため、メイン画面と同じ「期限が近い順」で並びます)。各行をタップすると`actionStartActivity<MainActivity>()`でアプリを開くのみで、ウィジェット上での完了操作などは行いません。表示は自動更新されないため、`TaskViewModel`の`addTask`/`toggleDone`/`updateTask`/`deleteTask`/`addSubtask`と`TaskCompletion.complete`の末尾で`refreshTaskWidget(context)`(`widget/TaskWidgetUpdater.kt`内のトップレベル関数)を呼び、タスクに変更があるたびに再描画をトリガーしています(`TaskCompletion.complete`はアプリ内・通知の「完了」アクションの両方から呼ばれるため、通知経由の完了もウィジェットに反映されます)。`refreshTaskWidget`は内部で`TaskWidget().updateAll(context)`を呼ぶだけの薄いラッパーですが、`updateAll`が投げた例外を`CancellationException`以外は`Log.e("TaskWidget", ...)`で握りつぶします。ウィジェットの再描画に失敗しても、直前に完了している呼び出し元のDB書き込み自体を失敗させたくないためで、もし実機でウィジェットが更新されない場合はlogcatをタグ`TaskWidget`で確認すると原因を切り分けられます。`AndroidManifest.xml`には`TaskWidgetReceiver`(`GlanceAppWidgetReceiver`)を`android:exported="true"`で登録し、ウィジェット情報は`res/xml/task_widget_info.xml`(`updatePeriodMillis`はOS側の最小値である30分に設定。`initialLayout`はGlanceライブラリ組み込みの`@layout/glance_default_loading_layout`をそのまま使用)で定義しています。**背景色**: `WidgetBackground`(`widget/WidgetBackground.kt`内の`enum class`。`TRANSPARENT`/`WHITE`/`BLACK`の3値で、`TRANSPARENT`は背景色・文字色とも上書きせず従来の見た目のまま)をウィジェットのインスタンスごとに個別選択できます。`task_widget_info.xml`の`android:configure`で`widget/TaskWidgetConfigureActivity.kt`を指定しており、ホーム画面にウィジェットを追加する際にシステムから自動的に起動されます(`ACTION_APPWIDGET_CONFIGURE`のintent-filterも`AndroidManifest.xml`に登録)。この設定画面は`AppWidgetManager.EXTRA_APPWIDGET_ID`で対象のウィジェットIDを受け取り、`AlertDialog`+`FilterChip`(縦に長くなるため`Modifier.verticalScroll`でスクロール可能)で背景色と表示するリストの両方を選択させ、「追加」確定時に`GlanceAppWidgetManager(context).getGlanceIdBy(appWidgetId)`で`GlanceId`に変換した上で`updateAppWidgetState(context, glanceId) { prefs -> prefs[TaskWidget.BACKGROUND_KEY] = background.name; prefs[TaskWidget.LIST_FILTER_KEY] = listFilter }`(`androidx.glance.appwidget.state`)により選択値を保存し、`refreshTaskWidget(context)`で再描画をトリガーしてから`RESULT_OK`で終了します(`GlanceAppWidget`には単一インスタンスだけを対象にした`update`関数は無いため、内部的には全ウィジェットインスタンスを対象にする`updateAll`を呼びますが、他のインスタンスは自身の設定を読み直すだけで見た目は変わりません)(何も選ばず閉じた場合は`RESULT_CANCELED`のままとなり、システムがウィジェットの追加自体を取り消します)。`TaskWidget`は`override val stateDefinition = PreferencesGlanceStateDefinition`を指定しており、これによりGlanceがウィジェットインスタンス(`GlanceId`)ごとに`Preferences`用のDataStoreを自動的に用意・永続化してくれるため、アプリ側で独自のキー管理を行う必要はありません。`provideGlance`側は`currentState<Preferences>()[TaskWidget.BACKGROUND_KEY]`で自インスタンスの選択値を読み出し、`WidgetBackground.fromName()`で復元して背景色(`GlanceModifier.background()`)と文字色(`TextStyle(color = ColorProvider(...))`)に反映します。**表示するリスト**: メイン画面のリストフィルタ(Issue #56で追加した「すべて」/「リスト未登録」/各リスト)と同じ選択肢を、`TaskWidget.LIST_FILTER_KEY`(`stringPreferencesKey`)としてウィジェットインスタンスごとに保存します。値は「すべて」を表す`TaskWidget.ALL_LISTS_VALUE`(`"ALL"`。キー未設定の場合もこれと同じ扱い)、「リスト未登録」を表す`TaskWidget.UNASSIGNED_LIST_VALUE`(`"UNASSIGNED"`。`listId == null`のタスクのみ)、またはタスクの`listId`を文字列化した値のいずれかです。`TaskWidgetConfigureActivity`は`AppDatabase.getInstance(context).taskListDao().getAll().first()`(`LaunchedEffect(Unit)`内)でリスト一覧を取得し、各リストを`FilterChip`として選択肢に並べます。`provideGlance`側は`prefs[LIST_FILTER_KEY]`を読み出し、未完了のトップレベルタスク一覧をさらに絞り込んでから表示します。

## 共有によるタスク追加

**共有によるタスク追加**: `app/src/main/java/com/toshi0907/oboetotte/share/ShareReceiverActivity.kt`が実体です。`AndroidManifest.xml`で`ACTION_SEND`/`ACTION_SEND_MULTIPLE`(いずれも`mimeType="*/*"`で写真に限らず任意のファイル形式を受け付ける)のintent-filterを持つ`exported="true"`のActivityとして登録しており、他のアプリの共有メニューにOboetotteが表示されます。確認・編集画面は挟まず、起動直後に`taskDao.insert`で「タスク(`yyyy/MM/dd HH:mm`形式のローカル日時)」という名前・デフォルト期限(`TaskViewModel.DEFAULT_DUE_DELAY_MILLIS`、登録時刻の1時間後。他のタスク登録と共有するため`private`から公開に変更)の新規タスクを即座に作成し`ReminderScheduler.schedule`を呼びます。`Intent.EXTRA_STREAM`から取得した共有ファイルの`Uri`(`ACTION_SEND`は単一、`ACTION_SEND_MULTIPLE`は複数)は、複数あってもすべて同じ1件の新規タスクへの添付ファイルとして`AttachmentStorage.copyToStorage`(既存の添付ファイル追加と同じ経路)で端末内にコピーし`taskAttachmentDao.insert`で保存します。`Intent.EXTRA_TEXT`から取得した共有テキストは、trim後の文字列全体が`android.util.Patterns.WEB_URL`に完全一致すればURL共有とみなし`normalizeUrl()`(`MainActivity.kt`内、他のタスク登録〈`EditTaskDialog`〉と共有するため`private`から公開に変更)を通してタスクの`url`に、一致しなければテキスト共有とみなしそのまま`memo`に格納します(ファイルと同時に共有された場合も両方保存します)。画面には何も表示せず(`Theme.Oboetotte.SnoozeDialog`の透過テーマを流用)、保存完了後に`Toast`で結果(添付件数・URL/メモの別を含む)を通知して`refreshTaskWidget`を呼んでから`finish()`します。所属リストは指定できないため常に`listId = null`(リスト未登録)になります。

## アプリ内アップデート

**アプリ内アップデート**: `app/src/main/java/com/toshi0907/oboetotte/update/`(`AppUpdateChecker`/`AppUpdateInstaller`/`AppUpdateNotifier`/`AppUpdateCheckSettings`)が実体です。Google Playを使わず`latest-debug`タグ(前述のCI/ビルドパイプライン参照)経由で配布しているため、Play Coreのアプリ内アップデートAPIは使えません。`versionCode`/`versionName`も固定値(`app/build.gradle.kts`、1/"1.0")で、CIが`main`への毎pushで`latest-debug`タグのAPKを上書きするだけのため、バージョン番号での新旧比較ができません。ビルド時にgitのコミットSHAを`BuildConfig.GIT_COMMIT_SHA`として埋め込む(`app/build.gradle.kts`内の`resolveGitCommitSha()`。GitHub Actions上のビルドでは自動設定される環境変数`GITHUB_SHA`を使い、無ければ`git rev-parse HEAD`にフォールバック、いずれも失敗すれば`"unknown"`。設定画面に現在のビルドを表示する用途にのみ使う)のに加えて、新旧判定には単調増加する**ビルド番号**を使います。コミットSHA同士は「等しいか」しか分からず順序を比較できないため(ローカルビルドのSHAが`latest-debug`と異なるだけで「新しい」と誤判定しうる)、GitHub Actions上のビルドでは実行のたびに増加する環境変数`GITHUB_RUN_NUMBER`を`resolveBuildNumber()`で読み取り`BuildConfig.BUILD_NUMBER`として埋め込みます(ローカルビルド等`GITHUB_RUN_NUMBER`が無い環境では`0`)。`latest-debug`リリースの本文にも同じ値を`ビルド番号: <n>`(`.github/workflows/android-build.yml`の`${{ github.run_number }}`)として埋め込んでおり、これと`BuildConfig.BUILD_NUMBER`を比較します。**`AppUpdateChecker.check()`**(ブロッキングI/O、呼び出し元が`Dispatchers.IO`上で呼ぶ想定は`attachment/AttachmentStorage`と同じ方針)は、GitHub API(`https://api.github.com/repos/.../releases/tags/latest-debug`、publicリポジトリのため認証不要。User-Agentヘッダ必須)を`java.net.HttpURLConnection`+`org.json`(いずれも標準ライブラリ、追加の依存無し)で叩き、レスポンスJSONの`body`から正規表現でビルド番号を抽出し、`BuildConfig.BUILD_NUMBER`(`0`以下なら判定不能として`CheckFailed`)より大きい場合のみ「更新あり」と判定します。結果は`sealed interface Result`(`UpdateAvailable(downloadUrl, buildNumber)`/`UpToDate`/`CheckFailed`〈ビルド番号が判定できない場合や通信エラー・パース失敗を含む〉)で返します。`MainActivity`の`setContent`内で`LaunchedEffect(Unit)`により起動のたびに自動チェックし(`updateCheckResult`としてComposeの状態に保持)、`TaskScreen`は`UpdateAvailable`の場合のみ既存の権限バナーと同じ見た目(`Card`+`TextButton`、ただし`primaryContainer`色でエラーではなく通常の通知として区別)で更新バナーを表示、`SettingsScreen`の「アップデート」セクションは結果の種類に応じたテキストと「更新を確認」ボタン(`onCheckForUpdate`で再チェック)を常時表示します。**最終確認時刻**: `AppUpdateChecker.check()`を呼ぶたび(起動時の自動チェック・「更新を確認」ボタン・後述のバックグラウンド定期チェックのいずれも)に`AppUpdateCheckSettings.recordCheckedAt(context, millis)`でSharedPreferences`app_update_check_settings`へ記録し、`SettingsScreen`の「アップデート」セクションに「最終確認: <日時>」として表示します。`TaskViewModel.updateLastCheckedAt`(`StateFlow<Long?>`)は初期値を`AppUpdateCheckSettings.getLastCheckedAt`から読み込みつつ、`backup/CloudBackupSettings.addLastResultChangeListener`と同じ考え方の`SharedPreferences.OnSharedPreferenceChangeListener`(`init`で登録・`onCleared`で解除)でSharedPreferences側の変更を直接購読するため、アプリを開いたままバックグラウンドの定期チェック(`AppUpdateCheckWorker`)が実行された場合もアプリ再起動無しに画面へ反映されます。**ダウンロード中の表示**: APKのダウンロード自体に時間がかかりインストールダイアログが出るまでボタンを押せたかどうか分かりづらかったため、`MainActivity`の`downloadAndInstallUpdate()`はダウンロード開始から完了(成功・失敗いずれも`finally`で解除)まで`isDownloadingUpdate`(Composeの状態)を`true`にし、`TaskScreen`のバナー・`SettingsScreen`の「ダウンロードしてインストール」ボタン双方でこの間ボタンを無効化しラベルを「ダウンロード中…」に変えます。**インストール**: `AppUpdateInstaller.download(context, url)`(同じくブロッキングI/O)が`filesDir/updates/`配下にAPKをダウンロードし、`hasInstallPermission(context)`(`PackageManager.canRequestPackageInstalls()`、API 26以降必須)が`false`なら`unknownSourcesSettingsIntent()`(`Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES`)で設定画面へ誘導、`true`なら`installIntent(context, file)`(`attachment/AttachmentStorage.openIntent`と同様`FileProvider`経由、`res/xml/file_paths.xml`に`updates/`を追加)で`ACTION_VIEW`+`application/vnd.android.package-archive`のIntentを起動しシステムのパッケージインストーラーにインストール確認を委ねます(自動インストールはできないため、ユーザーの最終確認は必ず挟まります)。`AndroidManifest.xml`に`INTERNET`・`REQUEST_INSTALL_PACKAGES`権限を追加しています。**バックグラウンドでの定期チェック**: アプリを開いていない間も新しいビルドに気づけるよう、`AppUpdateCheckScheduler`(`notification/LocationUpdateScheduler`と同様の構成)がWorkManagerの定期ジョブ`AppUpdateCheckWorker`(`CoroutineWorker`)を6時間間隔(`NetworkType.CONNECTED`制約付き。接続が無いタイミングではWorkManager側が復帰まで実行を保留する)でスケジュールします。`MainActivity`が起動のたびに`ensureScheduled`を呼びますが`ExistingPeriodicWorkPolicy.KEEP`のため既に動作中なら何もせず、位置情報の定期取得とは異なり常時有効な機能のため動的に停止する仕組みは持ちません。`AppUpdateCheckWorker`は`AppUpdateChecker.check()`を呼び、`UpdateAvailable`かつ`AppUpdateNotifier.shouldNotify(context, buildNumber)`(SharedPreferences`app_update_notifier`に記録した最後に通知したビルド番号と比較し、同じビルドに対して繰り返し通知しない)が`true`の場合のみ`AppUpdateNotifier.showNotification`で通知チャンネル`app_updates`の通知(タップでアプリを開くのみ。`notification/LocationReminderNotifier`と同様の組み立て)を表示します。`showNotification`は`NotificationManagerCompat.areNotificationsEnabled()`とチャンネルの`importance`(`IMPORTANCE_NONE`でないか)を`notify()`の直前に確認し、いずれかでブロックされていれば通知もSharedPreferencesへの記録も行わずに`false`を返します(通知がブロックされている間に記録だけ進んでしまうと、後でユーザーが通知を許可し直しても同じビルドについて二度と通知されなくなるため)。
